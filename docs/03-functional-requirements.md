# Aivo functional requirements

Each section owns one stable behavior. IDs are never reused; replaced or removed requirements remain with a status marker.

### REQ-IDENTITY-001 Personalized assistant identity

Aivo must present a naming page immediately after the initialization welcome page, show `请为我命名` above one focused text input prefilled with `Aivo`, and require one trimmed, non-empty, bounded name before continuing. Core owns validation and persists the confirmed value as non-secret global application configuration when initialization completes. The configured name is the visible label for the built-in Assistant, the empty-home title and supporting copy, the projectless application title, and the desktop document title. A missing historical value or omitted compatible-client input resolves to `Aivo`. Personalization never changes stable Agent IDs, package identity, protocol names, application-data paths, or other technical identifiers.

Acceptance: `AT-IDENTITY-001` covers defaulting, normalization, bounds and refusal, initialization persistence, restart and schema-v9 migration behavior, compatible omission, and consistent assistant/home/title presentation. `AT-UI-001` covers the naming page's wide, narrow, keyboard, disabled, and error states.

### REQ-PROVIDER-001 Provider configuration and health

Aivo must let the user configure and inspect supported provider accounts, resolve an available model, surface actionable authentication or dependency errors, and run provider diagnostics without placing credentials in renderer state or logs. After initialization, desktop settings must read configured Providers from the Core catalog, let the user refresh Aivo's shared Provider/model ecosystem catalog for subsequent add-Provider model selection, refresh an individual configured Provider's remote model list, add or connect one through the same connection flow used during initialization, and remove a whole Provider configuration only after explicit confirmation through the Core-owned deletion operation. A successful ecosystem refresh must replace the local public catalog cache and immediately reload the settings catalog. Ecosystem Providers whose recognized protocol has a compatible remote model-list operation must expose configured-Provider refresh; unsupported static protocols must explain the catalog-refresh alternative when invoked. A successful configured-Provider refresh must replace only that Provider's cached list and displayed list-default model through Core-owned persisted configuration and credentials. Neither refresh changes the application's active model preference; remote endpoint, authentication, and parsing failures remain actionable and preserve the previous catalog. For every supported Provider model catalog that returns a documented machine-readable capability declaration, Core must use its Provider-specific parser and persist each explicitly known capability dimension separately from its supported boolean. Anthropic structured native-tool declarations populate only the allowlisted Provider-hosted tool set; Mistral `capabilities.function_calling`, OpenRouter `supported_parameters`, and Cerebras public `capabilities` populate client-tool eligibility without creating hosted tools. The authenticated ChatGPT Codex catalog populates only typed code-owned compatibility facts for the built-in OpenAI OAuth route: context and compaction limits, reasoning efforts/default, verbosity/default, input modalities, service tiers/default, parallel-tool support, original image detail, Responses Lite selection, web-search representation, and the existing allowlisted `shell_type` local-tool eligibility. Codex account-native Provider capabilities are a separate adapter layer rather than model-catalog fields: the built-in OAuth route exposes its code-owned namespace-tool, image-generation, and web-search account contract, while every effective fallback route recomputes that contract. The shared OpenAI API-key route must ignore both Codex declarations and Codex account capabilities. Remote model messages, experimental tool names, tool modes, multi-Agent/review flags, and instruction-inclusion flags cannot replace Aivo prompts, create executable identities, or change Host policy. An explicit returned value overrides legacy static metadata for the same dimension, while missing, malformed, and unsupported catalog shapes remain unknown and are not inferred. Before first use of a selected model whose authoritative declaration metadata is missing or older than the Host-owned freshness window, Core performs one bounded best-effort catalog sync without a user action; failure preserves the previous cache and does not itself block the model request. Every local executable tool identity must already match the global `^[A-Za-z0-9_-]+$` Provider-safe contract with a 64-byte maximum before it enters a Provider request. Provider adapters must serialize and observe that exact canonical identity without encoding, decoding, escaping, or alias lookup.

Acceptance: `AT-PROVIDER-001` covers provider registry/configuration behavior, settings catalog/ecosystem-refresh/configured-provider-refresh/add/connect/confirmed-delete states, public catalog cache replacement, immediate add-flow model availability, persisted-config remote model refresh with per-Provider cache/default-list replacement, Anthropic/Mistral/OpenRouter/Cerebras/ChatGPT-Codex declaration parsing including every allowlisted Codex runtime field, known-versus-supported persistence, account-native capability catalog visibility, unknown-enum refusal, explicit-denial precedence, inert remote policy fields, OAuth/API-key route isolation, fallback capability recomputation, automatic missing-or-expired first-use sync, cache-preserving discovery failure, active-preference preservation, unchanged canonical tool names across declarations, history, final responses, and streams, plus the provider smoke path. `AT-UI-001` covers the settings loading, empty, error, busy, wide, and narrow states.

### REQ-PROJECT-001 Local project context

Aivo must let the user add or open a local project, maintain project-scoped runtime configuration, and isolate conversation, tool, worktree, and discovery context between projects.

Acceptance: `AT-PROJECT-001` covers project service and isolation behavior.

### REQ-PROJECT-002 Initial workspace for unscoped conversations

Aivo must present one local default directory during initialization, let the user accept it or select another directory, and persist the confirmed path before initialization completes. Aivo uses that same directory as the coding context for every temporary or otherwise projectless conversation. These conversations remain unscoped in project navigation. Aivo must not create per-conversation directories or silently switch a confirmed path. If the configured root is missing, Aivo recreates that exact root; an unconfigured path, a non-directory at that path, or a creation failure produces an actionable error without changing explicitly selected project behavior.

Acceptance: `AT-PROJECT-002` covers default-path presentation and confirmation, initialization validation, repeated unscoped conversation creation against one directory, exact-root recreation, explicit-project precedence, non-directory refusal, and absence of per-conversation directory creation.

### REQ-PROJECT-003 Agent project catalog and immutable session binding

Aivo must provide a trusted namespaced built-in extension that lets an eligible Agent query the bounded local project catalog, register an existing absolute local directory without creating or cloning content, and bind only its current unscoped coding conversation to an exact returned project. A renderer chooser may request the same binding by submitting the exact existing project ID and displayed root path as a typed resource reference; handwritten prompt text cannot bind a project. Project query is read-only; registration and association follow the active permission mode and identify the exact target. A conversation's first project association atomically updates its durable project ownership and coding context. The same association is idempotent, while switching, detaching, arbitrary-session mutation, association from a specialized workspace, and association with live interactive terminals are refused. After association, the next model request and desktop state use the bound project's workspace-dependent context without adding another unqualified core tool.

Acceptance: `AT-PROJECT-003` covers bounded query/pagination, existing-directory registration, hidden restoration, permission behavior, immutable and concurrent association, failure rollback, workspace refresh, and desktop project-state presentation.

### REQ-AGENT-001 Dynamic Agent mode management

Aivo must present exactly one visible code-owned built-in Agent, Assistant, as the composer and new-session default, while retaining only runtime-required summary, title, and scheduler workers as hidden built-ins. The “Extensions and MCP” management surface lets the user search, inspect, create, edit, reset, and delete supported definitions through Core-owned typed operations. Assistant appears without being eagerly copied into persistence; editing it creates a durable validated override, and resetting it removes only that override and restores the code default. Removed legacy built-in identifiers are not listed or manageable and resolve to Assistant only when encountered in historical sessions. A user-created global mode is durable and may be deleted only when no session or another managed mode references it. Hidden workers remain code-owned and unavailable to management. Core validates stable lowercase identifiers, display metadata, prompt, optional model and sampling settings, maximum steps, permission scope, primary/subagent role, and at most 16 unique associated subagent IDs before persistence and again before execution. Agent creation and editing must present eligible targets through a keyboard-operable multi-select dropdown; only primary-capable modes may own associations, and every target must be an existing visible subagent-capable non-self mode. Global management DTOs and stored definitions do not contain toolsets: Assistant retains its code-owned capability set and custom global modes receive the safe runtime default. Effective resolution applies code defaults, then durable global definitions, then existing project runtime configuration; project files remain project-scoped, may retain project-specific toolset policy and replace subagent associations, and are never rewritten by global CRUD. Successful changes are reflected by subsequent global/project catalog reads and conversation Agent pickers without an application restart.

Acceptance: `AT-AGENT-001` covers the single visible built-in Assistant default and retired-ID fallback, hidden worker protection, Assistant origin/reset, custom create/read/update/delete, persistence/restart, bounds and protected-ID refusal, session/association referenced-mode deletion and role-change refusal, toolset omission plus built-in/safe runtime capability restoration, effective global/project precedence, runtime prompt/model/tool/permission/association application, typed RPC behavior, search/editor states, and conversation-picker refresh.

### REQ-PROMPT-001 Validated prompt management

Aivo must provide a global Core-owned catalog for categorized Agent, protocol, auxiliary, task, dynamic-context, and quick prompts. Built-in defaults are embedded `aivo.prompt/v1` Markdown; bounded symlink-free managed files may override them. Core validates identity, category, policy, size, variables, required references, and complete rendering before an override can become active. Invalid working content remains visible with actionable diagnostics but the next execution uses the last validated revision or embedded default. One execution retains one immutable prompt snapshot. Required prompts may be edited and reset but not disabled or deleted; optional built-ins may be disabled; only bound custom Agent and quick prompts may be created and deleted subject to reference checks. Tool and parameter descriptions are inspectable but read-only. The associated-subagent explanation is not a managed protocol prompt: Core deterministically generates it from the effective validated Agent association list and omits it when that list is empty. Renderer management uses typed Core operations and cannot make prompt text authoritative for tools, permissions, credentials, structured envelopes, delegation targets, or execution. Global edits apply to later executions without restart; project instructions, Skills, extension context, MCP Prompts, and project runtime overlays remain independent and higher-precedence where already specified.

Acceptance: `AT-PROMPT-001` covers embedded catalog integrity, parsing and bounds, variable and reference validation, atomic save/reload, last-known-good restart recovery, required/optional/custom lifecycle, immutable execution snapshots, consumer rendering, Agent reference migration and compatibility, typed RPC behavior, top-bar routing, responsive editor states, external manual reload, and quick-prompt refresh.

### REQ-SESSION-001 Conversation and task execution

Aivo must let the user create or continue a conversation, submit a task, receive streaming progress, cancel execution, and recover or retry after an actionable failure without corrupting prior history. Immediate message submission may carry a bounded typed set of chooser-selected resource IDs; Core validates the entire set before event/turn creation and merges valid Skill, explicit tool-group, individual-tool, extension, or MCP selections into only that conversation. Each conversation owns an independent manual tool set and one automatic tool set. Manual activation remains until changed by the user; the six required core tools are not selectable and cannot be disabled through session state. Before the first primary request, auxiliary selection classifies whether the user is inspecting available capabilities or needs to use them: inspection initializes an empty durable automatic set but exposes the complete eligible concrete catalog to that one Provider request without a Host-owned expanded-tool count cap, while use persists every member of each selected explicit group and each selected individual tool as the stable automatic set. The automatic set then remains stable until the primary Agent explicitly requests a successful persistent replacement through the Host tool-selection control. Replacement never adds to or removes from the manual set. A selection made before a conversation exists is consumed by the next created conversation exactly once and is not a global default. Queued or steered input cannot carry resource references. A primary-capable mode with associated subagents may let the model autonomously call the existing bounded delegation tool only for those effective target IDs; a mode with no associations receives no delegation tool, and every call is revalidated before a child session is created. Delegation is task-driven rather than unconditional fan-out and retains existing depth, parallelism, cancellation, permission, result-order, and child-session lifecycle rules. Cancelling a turn keeps its user-visible history but terminalizes its owned execution and interactions; later model requests must not treat the cancelled turn's instructions or approvals as active work.

For each settled successful primary model request, Core must persist a bounded runtime summary without prompt, response, tool, credential, or raw Provider data. The summary owns one LLM step, request wall time, available first-token/decode timing, normalized Provider-reported input and output token counts, and cache-read counts together with whether the Provider actually supplied cache accounting. The desktop conversation must aggregate those persisted summaries into completed-turn and step counts, summed LLM duration, sampled average first-token latency and decode throughput, cache-hit percentage only across wholly cache-accounted input, and input/output totals beside the active composer. Unsupported readings and historical events without summaries are omitted rather than estimated, and no statistic is transmitted as remote telemetry.

Core must automatically compact settled model-visible conversation history when its safe estimated pressure reaches the configured percentage of the selected model's advertised context length, defaulting to 80%, while falling back to the existing conservative local capacity when model metadata is unavailable. Compaction preserves a bounded recent tail verbatim, consolidates older context into one durable summary, retains original events for user-visible history and recovery, and sends only the latest summary plus post-boundary messages in later Provider requests. The newest unanswered user request is never hidden by automatic compaction. Manual compaction uses the same bounded Core operation, requires an idle session, is cancellation-aware, and exposes only safe status/summary identifiers in its visible system note.

For automatic selection, the auxiliary model can select only an exact typed MCP or non-built-in extension source ID; it never selects concrete member names, generated Provider namespaces, standalone tools, or Skills. The Host expands a selected source locally to every currently registered, mode-eligible, globally visible concrete member. For use intent, every expanded canonical name—not the source ID—becomes the stable conversation automatic set and immutable Tool Snapshot membership; later source-catalog changes do not silently alter it. For inspection intent, the Host injects the complete eligible concrete catalog without a count cap, marks the durable automatic set initialized but empty, and freezes those names only in the first request's Tool Snapshot. The visible result contains only categorized extension/MCP/tool/skill resource summaries: each MCP/extension source appears once with its exact ID and injected member count, while concrete names remain internal to session state and the snapshot.

For the authenticated ChatGPT Codex route, Core must constrain the request to the selected model's recognized declared reasoning efforts, default reasoning, service tiers, default verbosity, parallel-tool support, input modalities, and image-detail support. A model explicitly declaring Responses Lite must receive its required header and developer `additional_tools` input item, no top-level hosted tools, disabled parallel tool calls, and all-turn reasoning context. Unsupported preferences are replaced only by a declared default or omitted; model names are never used to infer these facts. Account-native tools and Codex system Skills are available without a user import step only while a ChatGPT Codex OAuth account is configured; system Skills remain Host instructions rather than account mutation or execution authority. Bounded URL citations and search-result sources from complete or streaming responses must remain deduplicated in the final assistant result.

Acceptance: `AT-SESSION-001` covers session runtime, turn, streaming, cancellation, recovery, persisted successful-step timing/usage normalization and aggregation, malformed or unavailable metric omission, session-scoped and one-shot draft tool activation, request-only complete inspection injection, conversation-persistent use selection, explicit-group expansion, individual selection, and snapshot stability, one-event live initial-selection loading/result transitions, association-narrowed model delegation and forged/stale target refusal, Codex request-value constraints, Responses Lite body/header compatibility, image-input refusal, account-scoped Skill/tool availability and disconnect filtering, source preservation and streaming deduplication, pending-interaction cleanup, and isolation of a cancelled turn from the next model request.

### REQ-WORKSPACE-001 Sidebarless chat workspace

The desktop project chat workspace must prioritize the active conversation without reserving persistent left, right, or bottom panels. New conversation, new-window conversation, history, project context, extensions, settings, model, permission, agent-mode, attachment, microphone, and submit entry points must remain reachable through compact top-level or composer controls, while conversation and permission/question states preserve responsive layout and visible keyboard focus. The new-window conversation action sits after the in-window new-conversation action and opens an independent desktop window at an empty conversation without navigating, clearing, moving, or replacing the current window's active conversation. The new window is visibly cascaded a small distance to the right and below the window that opened it. Typing `@` at the composer caret opens a local, fuzzy-searchable mention chooser containing existing projects plus only globally enabled imported Skills, installed extensions, configured MCP sources, and optional built-in tools; the six required core tools remain available without appearing in the chooser. The chooser also exposes local “选择文件或文件夹” and “压缩上下文” actions. The compaction action consumes the query, invokes the existing idle-session Core compaction operation, provides bounded success/failure feedback, and creates neither submitted prompt text nor a typed resource reference. On macOS the file action consumes the active `@` query and directly opens one native file-or-directory chooser without an intermediate type confirmation; a selected file enters the existing attachment flow, while a selected directory enters the existing project-context flow. The action does not create a typed resource reference itself, and equivalent Windows/Linux combined-selection behavior remains subject to platform acceptance. The current project is identified and ordered first. Each extension and MCP source appears once at source level; their contributed tools are not expanded or duplicated under the tool group. Choosing a resource consumes the active `@` query, renders a visible removable resource tag inside the composer editing region, and records its typed stable identity; repeated selection is deduplicated and only one project tag may remain selected. On immediate submit, Core revalidates the selection and attaches the exact project, Skill, optional built-in tool, or source-level extension/MCP capabilities to that conversation; handwritten lookalike text has no binding effect. A project may initialize or bind an unscoped conversation but cannot switch an existing binding, while other resource selections merge with existing conversation activation and cannot override global disablement. Conversation Markdown renders host-native absolute file and folder paths in inline code or explicit links as keyboard-operable local links; an explicit click opens the resolved path through the desktop bridge and operating-system default application, while relative or foreign-platform paths remain inert and failures are actionable. Persistent or top-bar-triggered standalone right activity panels and bottom terminal panels, their resize handles, and their top-bar triggers are not mounted in this workspace; a user-opened contextual inspector governed by `REQ-TOOL-002` may temporarily share the chat width.

Acceptance: `AT-WORKSPACE-001` combines lint/build with wide and narrow screenshots plus focused acceptance for navigation reachability, independent new-window conversation creation with current-window preservation, composer controls, `@` chooser filtering, keyboard selection/dismissal, the combined file-or-folder local action, typed selection transport, clickable host-native absolute paths with source-location handling and open failures, scrolling, overflow, absence of auxiliary panel chrome, and empty/conversation states.

### REQ-TOOL-001 Controlled local tool execution

Aivo must expose the unqualified `read`, `bash`, `edit`, and `write` execution primitives followed by the same-level Host controls `update_plan` and `ask_user` to a default coding Agent in stable order, plus the Host-owned `tool_resolve` control that replaces the conversation's automatic tool set when the Agent identifies a concrete missing capability. Registered tools default to globally visible for future selection except the six required core tools, which are always active and omitted from selection surfaces, and code-owned Provider-declaration or Provider-account tools, which are dormant and unavailable to manual or auxiliary selection. The user may globally hide or restore an exact canonical tool other than the required `read`, `bash`, `edit`, `write`, `update_plan`, and `ask_user` tools. A globally hidden tool remains manageable but is excluded from new conversation choices, typed resource references, and auxiliary candidates; it is not retroactively removed from a conversation that already selected it. The six required core tools are omitted from global management, per-conversation activation, and composer resource-selection surfaces. Global and session updates cannot disable them, and legacy globally disabled rows or session `disabledCoreTools` metadata do not suppress them; ordinary permission, Provider compatibility, Tool Snapshot, and Execution Environment controls still apply. Permission mode offers only request approval and full access. Core rejects new automatic-approval values, while a historical stored `auto_approve` value is read and evaluated as request approval so it cannot retain automatic execution authority. Selecting an eligible optional built-in tool through the composer mention chooser merges it into the same conversation's manual set. The optional built-in `grep`, `find`, and `ls` tools are registered after those defaults, remain off until manually or automatically selected for a conversation, and use the same global visibility boundary. Workspace Registry construction must directly register `update_plan` and `ask_user` as reserved, non-toggleable core Host controls; they are invoked only by structured tool calls, enter every eligible immutable Tool Snapshot, and retain their existing plan-state and user-interaction lifecycle semantics. Other Host Agent-control, goal, and automation executor implementations must not be registered directly; they become executable only through an eligible versioned dynamic contribution and its ordinary trust, selection, snapshot, and permission checks. A Provider-hosted server tool is not a local executable or default primitive: when authoritative dynamic metadata for the selected model explicitly reports one, an allowlisted Provider/transport/version adapter must declare it automatically in that Provider request without user activation. Unknown metadata, static model-name capability tables, unsupported adapters, and configured native-tool disablement must not produce an automatic declaration. Provider-hosted calls execute on Provider infrastructure and remain outside the local Registry and local Tool Snapshot. For the built-in OpenAI OAuth Codex route, recognized `shell_type` metadata retains or suppresses the existing `bash` declaration. A recognized `web_search_tool_type` automatically exposes the existing canonical search capability when web search is enabled: ordinary Responses receives a Provider-hosted `web_search` declaration outside the local Registry and Tool Snapshot, while Responses Lite or an explicit local route activates the dormant permission-controlled `web_search` executor backed by the authenticated Codex search operation and includes it in the immutable snapshot. The account-native `image_gen.imagegen` tool is registered under its Responses namespace and activates only for the built-in ChatGPT Codex OAuth route; it calls the Codex generation/edit endpoints with the active account, supports either up to five workspace-relative edit images or up to five recent conversation images, bounds request/response/image bytes, writes a new non-symlinked local PNG artifact, and returns only bounded metadata plus a transient model image attachment. Its base64 provider payload is excluded from logs and durable tool results. `cached`, `indexed`, `live`, and `disabled` search modes and declared text-versus-image search content are preserved. Unknown or unsupported values fail closed, API-key routes ignore Codex declarations and account tools, Provider compatibility gating and configured disablement of non-required capabilities win, and every activated local tool must enter the immutable Tool Snapshot and existing mode, Execution Environment, permission, cancellation, and output controls before execution. Responses namespace calls preserve and validate both namespace and canonical member name. The four primitives share one active Execution Environment and retain validated inputs, explicit permission policy, bounded model output, cancellation, deterministic cleanup, and safe recorded results. Workspace file paths supplied to `read`, `edit`, and `write` are relative to the active workspace root; only an exact retained-output reference returned by the Host may be absolute for `read`. `read` reads one bounded text or supported image file; `bash` runs one foreground non-interactive Bash command; `edit` atomically applies one batch of exact, unique, non-overlapping replacements against one original file snapshot; and `write` atomically creates or completely overwrites one text file. `grep`, `find`, and `ls` provide bounded workspace content search, path matching, and directory listing without becoming default tools. The removed development names, including `apply_patch`, have no execution aliases. Workspace policy and confirmation are correctness controls, not process containment; the active local or external Execution Environment owns actual authority and isolation.

Each native permission-mode selection also persists a non-secret global default, initially request approval. Core copies the current default into a new coding conversation as that session's independent permission rule; changing the default must not change an existing conversation.

Every registered local tool is either an individual selectable resource or a member of one explicit selection group. Registration without selection-group metadata is individual even when several tools share a source, namespace, category, or extension. A group has one canonical ID, display name, optional description, and one or more concrete member tools; every member retains its own executable canonical identity. Manifest v2 may declare `contributes.toolGroups`, while an MCP adapter declares one group for the server's concrete tools and Host resource utilities. A tool cannot belong to more than one group, and inconsistent or undeclared membership is rejected before catalog publication.

The auxiliary tool selector receives only the user intent plus bounded single-line `kind:id：display-name｜description` entries: exactly one entry for each eligible explicit group and one entry for each eligible individual tool. It never receives the concrete member names of a grouped candidate. When an MCP group description is blank, the Host assembles every current eligible member name and description as its bounded fallback; a blank extension group description stays blank. Descriptions are untrusted data. Its only valid response is a strict JSON object containing an exact `intent` classification of `inspect` or `use` and a unique `resources` array of exact `{kind,id}` MCP/extension/tool identities. A grouped identity is indivisible: the auxiliary model can select only the group, and the Host expands every currently eligible member; an individual identity expands only itself. Skills and concrete members of a group are invalid selector output. `inspect` requires an empty resource array and makes the Host inject the complete eligible catalog for one request; `use` persists every validated expansion. The Host owns classification, membership, eligibility, schemas, Provider serialization, lifetime, and snapshot assembly. The visible initial-selection note contains only bounded state, typed group/individual/skill summaries, member counts, and lifetime—never concrete grouped member names or selector internals. `tool_resolve` is use-only and persistent.

Acceptance: `AT-TOOL-001` covers the exact default registry and schemas including always-on core tools omitted from management/activation/mention surfaces and legacy disabled-preference compatibility, registered but non-default `grep`/`find`/`ls`, absence of directly registered Agent-control/plan/question/goal/automation tools, dynamic-contribution activation, and removed-name refusal, authoritative dynamic Provider-tool declaration, Codex-declared shell filtering, automatic hosted and Responses Lite/local search exposure, account-native image generation/edit routing and bounds, namespace preservation and mismatch refusal, search modes/content types, hosted-tool snapshot exclusion, local search snapshot and permission enforcement, OAuth/API-key isolation, fallback tool-set recomputation, unknown/static-metadata refusal, configured native-tool disablement, Provider server-tool serialization, immutable snapshot membership, strict inspect/use classification, explicit grouped and individual registration, group-only auxiliary disclosure and selection, uncapped complete group expansion, complete request-only inspection beyond the former 64-tool limit, persistent use selection, safe one-event live initial-selection recording, relative-path guidance, text/image reads, Bash output/artifacts/timeouts, bounded search/find/list behavior, exact atomic edit/write behavior, the request-approval/full-access mode contract, removed automatic-approval refusal and historical fail-closed fallback, permission and environment boundaries, cancellation/cleanup including invalidation of turn-owned pending approvals, absence of execution aliases, historical fallback rendering, and safe result recording.

### REQ-TOOL-002 Contextual tool activity inspector

The initial selection disclosure must identify `request` lifetime as a one-request temporary injection and `conversation` lifetime as a persistent automatic set. Its resource contract recognizes only extension, MCP, tool, and skill; Agent modes are configuration rather than injectable resources. Running and failed payloads do not require a lifetime; a completed payload with missing or unknown lifetime makes the typed payload malformed and retains the ordinary system-note fallback.

The desktop conversation must present the Host's typed initial automatic-tool selection note as an accessible disclosure before later tool activity. It is collapsed by default, keeps its current state summary visible while the auxiliary selector is running or after it settles, and updates the same row in place to resource-level groups or an explicit empty/failure state available by expanding the disclosure. Each selected explicit group appears once under its category with its exact group ID/display name and concrete member count; each selected individual tool and Skill appears separately. The renderer merges live note changes by event identity, still loads the final persisted result from history, and falls back to the ordinary system-note rendering when the typed payload is malformed. The desktop conversation must present every visible tool call as an accessible label containing the tool's name, arranged from left to right in a compact wrapping activity region without interleaved execution-description text. Activating any label or the surrounding activity region must open the same contextual right-side inspector for that complete activity, not a single-label view. The inspector must automatically open when a new tool call is received in an active conversation, without opening merely because historical calls were loaded. Manually closing it suppresses further automatic opening for that conversation while preserving manual label activation; a different or newly created conversation resets that suppression. The inspector must animate into the chat layout and present every tool call in the activity as one timeline ordered by call time, using an associated invocation description as the first applicable item title only when that description exists; immediately following calls with the same description must not repeat it, and calls without an invocation description must not render a title. Every item shows the tool name as supporting text alongside execution status. Each timeline item must open and dismiss an overlapping in-panel detail view. When a tool call carries a Host-derived reference to an associated isolated extension `tool-detail` view, or to a tool-associated `page` fallback, that Web page must become the overlapping detail view automatically. A newly selected call with the same Host-resolved extension ID, View ID, and surface must reuse the mounted isolated WebContents and receive a bounded latest-wins context update without navigation or a loading fallback; changing View identity or closing the detail tears it down, and reopening recreates it. Unavailable views must retain the native bounded detail fallback. The inspector must not reintroduce a persistent auxiliary workspace or terminal panel and must preserve responsive layout, keyboard focus, safe result rendering, and live status updates.

### REQ-EXTENSION-001 Skills, plugins, and MCP

Initial tool-resource auxiliary selection must distinguish `inspect` from `use`. Inspection exposes the complete currently eligible concrete catalog to exactly one primary Provider request without a Host-owned concrete-tool count cap, persists no automatic names, and initializes an empty durable automatic set; use persists every member of validated explicit groups and each validated individual tool. Later `tool_resolve` selection is always use-only and conversation-persistent. Request-only inspection tools participate in only that request's immutable Tool Snapshot and retain all global visibility, readiness, mode, registration, permission, and stale-call checks. The strict auxiliary decision contains only classification and exact grouped-or-individual resource identities; the Host owns expansion, membership, lifetime, and categorized visible summaries.

The desktop MCP settings flow must support both environment-reference Bearer authentication and one-time direct Bearer-token entry. Direct values cross only the privileged save boundary, become Host-owned secure-store references immediately, are never returned or prefilled, and are absent from SQLite, renderer persistence, catalogs, logs, and diagnostics. Saving without a replacement preserves an existing reference, while failed save or authentication-mode replacement compensates secret state.

Aivo must discover supported built-in, process, local-service, external-service, and static extensions from the Manifest/API v2 language-neutral contract without executing untrusted code; every other version pair, including v1, is rejected without fallback or automatic conversion. The legacy `aivo.plugin.json` and `.aivo-plugin/plugin.json` package formats, JSONL plugin process runtime, plugin RPCs, and plugin tool/hook/provider contribution paths are unsupported and are never discovered, started, adapted, or exposed. Trust, source enablement, readiness, global per-tool visibility, eligibility, conversation activation, authorization, and execution are distinct states. Before the first primary model request, the Host prepares a bounded eligible resource catalog across imported Skills, Manifest v2 extensions, and MCP adapters; globally disabled sources and globally hidden exact tools are excluded before the auxiliary resolver sees one Host-owned candidate per explicit selection group and one per individual registration. MCP source and concrete-tool metadata used by this Host-only catalog is independent of Agent-visible executors: the primary Agent receives no general MCP source-enumeration tool and sees only concrete MCP tools selected for its task. The primary Agent always receives `tool_resolve` and may call it with a concise missing capability; the Host then invokes the same bounded grouped-or-individual auxiliary selection over current eligible candidates, expands validated resource identities locally, and atomically replaces the conversation's complete concrete automatic tool set for the next model step. Replacement does not accumulate, create warm leases, or alter manually activated tools. An immediate submit may additionally carry chooser-selected typed Skill, extension, MCP, explicit tool-group, or individual-tool IDs. Core revalidates them against the same current catalog, merges an enabled Skill into that conversation's active instructions, and expands a grouped resource only to its currently registered globally visible members while an individual resource expands only itself. The Host—not the auxiliary model—injects canonical summaries for selected Skills, loads full Skill instructions only for that validated subset, injects selected extension context, and freezes exact selected tool registration and schema identities in a Tool Snapshot assembled from the six required core tools, `tool_resolve`, the conversation's manual set, its current automatic set, and separately authorized mode controls. Catalog preparation may establish readiness or refresh an already enabled source, but selection cannot install, import, trust, enable, bind credentials, authorize, or execute a tool. Skill/context selection remains request-scoped, while manual and automatic tool sets belong only to their conversation. Global visibility changes affect future automatic/manual selection and do not revoke an existing conversation selection. Every executable canonical tool name is an ASCII `_`/`-`-namespaced identifier matching the global Provider-safe contract before registration. Manifest v2 rejects invalid contributed names and invalid `toolGroups`; generated MCP adapter names and selection-group IDs follow the same rule while retaining the upstream MCP name separately for execution. The same canonical concrete name remains authoritative through catalogs, activation, Tool Snapshots, Provider declarations and history, returned calls, permission evaluation, execution, UI emission, and persistence; collisions are rejected and no Provider wire alias exists. Group membership is registration-owned metadata and cannot be inferred from source, namespace, or category. Tool-resource auxiliary selection receives only the intent and sanitized group/individual display lines and cannot author membership or injected summary content. Extension processes, streams, calls, services, artifacts, and views have bounded output/backpressure, cancellation, draining, restart/update behavior, and deterministic teardown. A supervised local service may retain a fixed loopback URL or use a versioned bounded readiness handshake after binding an operating-system-assigned loopback port; the Host validates the announced root HTTP origin, owns the bearer and current-generation endpoint, and rejects timeout, overflow, malformed, non-loopback, or stale endpoints before readiness. For an extension tool associated through Manifest v2 `views[].tools`, the Host may add a bounded immutable view reference to the tool's UI details, preferring a declared `tool-detail` surface and using `page` only as a fallback; extension-returned data cannot select another extension, view, route, or Host surface. Complex extension Web views use isolated Host surfaces without Node integration, privileged preload access, ambient credentials, or unrestricted navigation, including when their Web contents is embedded into the main window's contextual inspector. An embedded View is mount-identified by its Host-resolved extension, View, and surface; when only the selected tool-call context changes, Electron main retains that isolated WebContents, replaces only the bounded Host context with a monotonic revision, and notifies the page through the versioned bridge. Stale mounts and context updates cannot retarget another View or change its origin, backend, token, actions, route, or surface.

When an OpenAI account is connected through ChatGPT Codex OAuth, Core automatically synchronizes every installed Codex `.system` Skill as a read-only `codex-system` Skill without creating import candidates or requiring a user action. If that Codex installation catalog is unavailable, Core materializes the reviewed built-in fallback set for image generation, official OpenAI documentation, plugin creation, review, Skill creation, and Skill installation under Aivo-owned system storage. System Skill metadata records its Codex origin, adapter version, and required account tool where applicable; a user Skill with the same normalized name is preserved rather than overwritten. System Skills participate in the existing Host-owned progressive-disclosure resolver, cannot be edited or deleted, can be disabled, and never grant credentials, permissions, tools, or provider availability.

An MCP source may capture a bounded non-secret functional description and stores an omitted description as empty. For an existing source, its edit surface may explicitly ask the configured auxiliary model to draft that description from every current stored discovered tool name and description. Core sends no endpoint, command, arguments, environment, headers, roots, authentication data, credential references, or executable tools, treats tool text as untrusted data, and returns bounded plain text that replaces only the unsaved description draft. A missing auxiliary model, empty tool catalog, catalog that cannot represent every member within Host bounds, cancellation, or Provider failure is actionable and does not save, probe, start, or mutate the source. For automatic selection only, a blank stored MCP group description is supplemented by a non-persisted deterministic assembly of every current eligible member name and description. Every extension selection group uses its validated Manifest group description without a source-description fallback. Auxiliary selection presents one exact typed ID for the MCP group and selecting it expands all current eligible members locally. Global per-tool hiding remains authoritative during expansion.

Resource management and selection surfaces use exactly four injectable categories: extensions, MCP, tools, and Skills. The desktop exposes their shared management surface as a dedicated `/extensions` route with the same full-window navigation shell as other global management pages; legacy project-scoped extension URLs redirect to that route instead of opening a drawer. The global tools category lists globally manageable optional built-in and trusted Aivo executors while omitting the six required core tools and dormant Provider-declaration tools. Skill management collapses compatibility-directory candidates by normalized name, omits a candidate while a Skill with that name is installed, and restores one candidate after the installed Skill is deleted. An installed Aivo-managed Skill exposes an edit action for its description and instruction body while keeping its stable name immutable; Core reads and atomically saves only the validated `SKILL.md` inside Aivo-managed Skill storage, rejects stale revisions, and refreshes the returned metadata and content hash. Agent modes remain manageable through a separate secondary management action but are not a fifth resource category. Every surface derives grouping only from explicit selection-group metadata: an individual registration is one row and one switch, while a grouped registration is one row that discloses every concrete member but exposes only one group-level switch. Source, namespace, category, and extension identity never create an implicit group. Group switching applies the same enabled state to every current concrete member. A built-in Aivo executor may therefore be individual or explicitly grouped even when implemented through the trusted Manifest runtime; MCP adapters expose one explicit server group.
