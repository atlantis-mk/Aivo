# Aivo functional requirements

Each section owns one stable behavior. IDs are never reused; replaced or removed requirements remain with a status marker.

### REQ-PROVIDER-001 Provider configuration and health

Aivo must let the user configure and inspect supported provider accounts, resolve an available model, surface actionable authentication or dependency errors, and run provider diagnostics without placing credentials in renderer state or logs. After initialization, desktop settings must read configured Providers from the Core catalog, let the user add or connect one through the same connection flow used during initialization, and remove a whole Provider configuration only after explicit confirmation through the Core-owned deletion operation. Every local executable tool identity must already match the global `^[A-Za-z0-9_-]+$` Provider-safe contract with a 64-byte maximum before it enters a Provider request. Provider adapters must serialize and observe that exact canonical identity without encoding, decoding, escaping, or alias lookup.

Acceptance: `AT-PROVIDER-001` covers provider registry/configuration behavior, settings catalog/add/connect/confirmed-delete states, unchanged canonical tool names across declarations, history, final responses, and streams, plus the provider smoke path. `AT-UI-001` covers the settings loading, empty, error, busy, wide, and narrow states.

### REQ-PROJECT-001 Local project context

Aivo must let the user add or open a local project, maintain project-scoped runtime configuration, and isolate conversation, tool, worktree, and discovery context between projects.

Acceptance: `AT-PROJECT-001` covers project service and isolation behavior.

### REQ-PROJECT-002 Initial workspace for unscoped conversations

Aivo must present one local default directory during initialization, let the user accept it or select another directory, and persist the confirmed path before initialization completes. Aivo uses that same directory as the coding context for every temporary or otherwise projectless conversation. These conversations remain unscoped in project navigation. Aivo must not create per-conversation directories or silently switch a confirmed path. If the configured root is missing, Aivo recreates that exact root; an unconfigured path, a non-directory at that path, or a creation failure produces an actionable error without changing explicitly selected project behavior.

Acceptance: `AT-PROJECT-002` covers default-path presentation and confirmation, initialization validation, repeated unscoped conversation creation against one directory, exact-root recreation, explicit-project precedence, non-directory refusal, and absence of per-conversation directory creation.

### REQ-PROJECT-003 Agent project catalog and immutable session binding

Aivo must provide a trusted namespaced built-in extension that lets an eligible Agent query the bounded local project catalog, register an existing absolute local directory without creating or cloning content, and bind only its current unscoped coding conversation to an exact returned project. A renderer chooser may request the same binding by submitting the exact existing project ID and displayed root path as a typed resource reference; handwritten prompt text cannot bind a project. Project query is read-only; registration and association follow the active permission mode and identify the exact target. A conversation's first project association atomically updates its durable project ownership and coding context. The same association is idempotent, while switching, detaching, arbitrary-session mutation, association from a specialized workspace, and association with live interactive terminals are refused. After association, the next model request and desktop state use the bound project's workspace-dependent context without adding another unqualified core tool.

Acceptance: `AT-PROJECT-003` covers bounded query/pagination, existing-directory registration, hidden restoration, permission behavior, immutable and concurrent association, failure rollback, workspace refresh, and desktop project-state presentation.

### REQ-AGENT-001 Dynamic Agent mode management

Aivo must present visible Agent modes in the “Extensions and MCP” management surface and let the user search, inspect, create, edit, reset, and delete supported definitions through Core-owned typed operations. Current visible code defaults appear as built-in modes without eagerly copying them into persistence. Editing a built-in creates a durable validated override, and resetting it removes only that override and restores the current code default. A user-created global mode is durable and may be deleted only when no session or another managed mode references it. Hidden summary, title, scheduler, and compatibility-only worker modes remain code-owned and unavailable to management. Core validates stable lowercase identifiers, display metadata, prompt, optional model and sampling settings, maximum steps, permission scope, primary/subagent role, and at most 16 unique associated subagent IDs before persistence and again before execution. Only primary-capable modes may own associations, and every target must be an existing visible subagent-capable non-self mode. Global management DTOs and stored definitions do not contain toolsets: built-ins retain code-owned capability sets and custom global modes receive the safe runtime default. Effective resolution applies code defaults, then durable global definitions, then existing project runtime configuration; project files remain project-scoped, may retain project-specific toolset policy and replace subagent associations, and are never rewritten by global CRUD. Successful changes are reflected by subsequent global/project catalog reads and conversation Agent pickers without an application restart.

Acceptance: `AT-AGENT-001` covers built-in listing/origin/reset, custom create/read/update/delete, persistence/restart, bounds and protected-ID refusal, session/association referenced-mode deletion and role-change refusal, toolset omission plus code/safe runtime capability restoration, effective global/project precedence, runtime prompt/model/tool/permission/association application, typed RPC behavior, search/editor states, and conversation-picker refresh.

### REQ-SESSION-001 Conversation and task execution

Aivo must let the user create or continue a conversation, submit a task, receive streaming progress, cancel execution, and recover or retry after an actionable failure without corrupting prior history. Immediate message submission may carry a bounded typed set of chooser-selected resource IDs; Core validates the entire set before event/turn creation and merges valid Skill/tool/source selections into only that conversation. Each conversation owns an independent manual tool set and one bounded automatic tool set. Manual activation and explicit core-tool disablement remain until changed by the user; the automatic set is initialized for the first task and remains stable until the primary Agent explicitly requests a successful replacement through the Host tool-selection control. Replacement never adds to or removes from the manual set. A selection made before a conversation exists is consumed by the next created conversation exactly once and is not a global default. Queued or steered input cannot carry resource references. A primary-capable mode with associated subagents may let the model autonomously call the existing bounded delegation tool only for those effective target IDs; a mode with no associations receives no delegation tool, and every call is revalidated before a child session is created. Delegation is task-driven rather than unconditional fan-out and retains existing depth, parallelism, cancellation, permission, result-order, and child-session lifecycle rules. Cancelling a turn keeps its user-visible history but terminalizes its owned execution and interactions; later model requests must not treat the cancelled turn's instructions or approvals as active work.

For automatic selection, an MCP or extension is selected as one Host-owned capability group and then expanded locally to all of that source's currently registered, mode-eligible, globally visible concrete tools. The expanded canonical names—not the group name—become the stable conversation automatic set and immutable Tool Snapshot membership; later source-catalog changes do not silently alter it.

Acceptance: `AT-SESSION-001` covers session runtime, turn, streaming, cancellation, recovery, session-scoped and one-shot draft tool activation, source-group expansion and snapshot stability, association-narrowed model delegation and forged/stale target refusal, pending-interaction cleanup, and isolation of a cancelled turn from the next model request.

### REQ-WORKSPACE-001 Sidebarless chat workspace

The desktop project chat workspace must prioritize the active conversation without reserving persistent left, right, or bottom panels. New conversation, history, project context, extensions, settings, model, permission, agent-mode, attachment, microphone, and submit entry points must remain reachable through compact top-level or composer controls, while conversation and permission/question states preserve responsive layout and visible keyboard focus. Typing `@` at the composer caret opens a local, fuzzy-searchable mention chooser containing existing projects plus only globally enabled imported Skills, installed extensions, configured MCP sources, and built-in tools. The chooser also exposes one local “选择文件或文件夹” action. On macOS it consumes the active `@` query and directly opens one native file-or-directory chooser without an intermediate type confirmation; a selected file enters the existing attachment flow, while a selected directory enters the existing project-context flow. The action does not create a typed resource reference itself, and equivalent Windows/Linux combined-selection behavior remains subject to platform acceptance. The current project is identified and ordered first. Each extension and MCP source appears once at source level; their contributed tools are not expanded or duplicated under the tool group. Choosing a resource consumes the active `@` query, renders a visible removable resource tag inside the composer editing region, and records its typed stable identity; repeated selection is deduplicated and only one project tag may remain selected. On immediate submit, Core revalidates the selection and attaches the exact project, Skill, built-in tool, or source-level extension/MCP capabilities to that conversation; handwritten lookalike text has no binding effect. A project may initialize or bind an unscoped conversation but cannot switch an existing binding, while other resource selections merge with existing conversation activation and cannot override global disablement. Persistent or top-bar-triggered standalone right activity panels and bottom terminal panels, their resize handles, and their top-bar triggers are not mounted in this workspace; a user-opened contextual inspector governed by `REQ-TOOL-002` may temporarily share the chat width.

Acceptance: `AT-WORKSPACE-001` combines lint/build with wide and narrow screenshots plus focused acceptance for navigation reachability, composer controls, `@` chooser filtering, keyboard selection/dismissal, the combined file-or-folder local action, typed selection transport, scrolling, overflow, absence of auxiliary panel chrome, and empty/conversation states.

### REQ-TOOL-001 Controlled local tool execution

Aivo must expose exactly the unqualified `read`, `bash`, `edit`, and `write` execution primitives to a default coding Agent in stable order, plus the Host-owned `tool_resolve` control that replaces the conversation's automatic tool set when the Agent identifies a concrete missing capability. Registered tools default to globally visible for future selection; the user may globally hide or restore an exact canonical tool. A globally hidden tool remains manageable but is excluded from new conversation choices, typed resource references, and auxiliary candidates; it is not retroactively removed from a conversation that already selected it. The user may separately disable or restore an eligible core tool for one conversation (or the one pending new conversation); selecting an eligible built-in tool through the composer mention chooser merges it into the same conversation's manual set. An explicitly disabled core tool is omitted from that conversation's Provider request and Tool Snapshot, while missing global and session preference state retains all four defaults. The four primitives share one active Execution Environment and retain validated inputs, explicit permission policy, bounded model output, cancellation, deterministic cleanup, and safe recorded results. Workspace file paths supplied to `read`, `edit`, and `write` are relative to the active workspace root; only an exact retained-output reference returned by the Host may be absolute for `read`. `read` reads one bounded text or supported image file; `bash` runs one foreground non-interactive Bash command; `edit` atomically applies one batch of exact, unique, non-overlapping replacements against one original file snapshot; and `write` atomically creates or completely overwrites one text file. `apply_patch` and specialized file, Git, test, build, formatting, diagnostic, terminal, LSP, web, automation, and sub-Agent executors are not default execution tools and have no execution aliases. Workspace policy and confirmation are correctness controls, not process containment; the active local or external Execution Environment owns actual authority and isolation.

The auxiliary tool selector receives only the user intent plus bounded single-line `name：description` entries for eligible MCP/extension capability groups. A missing description is represented by an empty value after `：` and does not remove the group. Descriptions are untrusted data. Its only valid response is a bare strict JSON array of unique exact candidate group names; the Host validates those names and owns all concrete membership, eligibility, Schema lookup, Provider serialization, and snapshot assembly.

Acceptance: `AT-TOOL-001` covers the exact registry and schemas including default and explicitly disabled core-tool surfaces, strict source-group selection and local expansion, relative-path guidance, text/image reads, Bash output/artifacts/timeouts, exact atomic edit/write behavior, permission and environment boundaries, cancellation/cleanup including invalidation of turn-owned pending approvals, direct `apply_patch` removal, historical fallback rendering, and safe result recording.

### REQ-TOOL-002 Contextual tool activity inspector

The desktop conversation must present every visible tool call as an accessible label containing the tool's name, arranged from left to right in a compact wrapping activity region without interleaved execution-description text. Activating any label or the surrounding activity region must open the same contextual right-side inspector for that complete activity, not a single-label view. The inspector must automatically open when a new tool call is received in an active conversation, without opening merely because historical calls were loaded. Manually closing it suppresses further automatic opening for that conversation while preserving manual label activation; a different or newly created conversation resets that suppression. The inspector must animate into the chat layout and present every tool call in the activity as one timeline ordered by call time, using an associated invocation description as the first applicable item title only when that description exists; immediately following calls with the same description must not repeat it, and calls without an invocation description must not render a title. Every item shows the tool name as supporting text alongside execution status. Each timeline item must open and dismiss an overlapping in-panel detail view. When a tool call carries a Host-derived reference to an associated isolated extension `tool-detail` view, or to a tool-associated `page` fallback, that Web page must become the overlapping detail view automatically. A newly selected call with the same Host-resolved extension ID, View ID, and surface must reuse the mounted isolated WebContents and receive a bounded latest-wins context update without navigation or a loading fallback; changing View identity or closing the detail tears it down, and reopening recreates it. Unavailable views must retain the native bounded detail fallback. The inspector must not reintroduce a persistent auxiliary workspace or terminal panel and must preserve responsive layout, keyboard focus, safe result rendering, and live status updates.

Acceptance: `AT-TOOL-002` combines focused timeline-title and same-identity View-reuse regression coverage, lint/build, and wide and narrow interaction screenshots covering per-tool naming, left-to-right wrapping, omission of interleaved execution descriptions, non-repeating consecutive invocation descriptions, omitted titles for calls without descriptions, label and activity-region activation, complete activity coverage, call-time ordering and status, live-call automatic opening, historical-load non-opening, per-conversation manual-close suppression and reset, push-open/close animation, stacked native and extension Web detail navigation, same-identity context switching without reload, different-identity and close teardown/reopen/fallback, long and missing content, repeated selection, and running, approval, success, and failure states.

### REQ-EXTENSION-001 Skills, plugins, and MCP

The desktop MCP settings flow must support both environment-reference Bearer authentication and one-time direct Bearer-token entry. Direct values cross only the privileged save boundary, become Host-owned secure-store references immediately, are never returned or prefilled, and are absent from SQLite, renderer persistence, catalogs, logs, and diagnostics. Saving without a replacement preserves an existing reference, while failed save or authentication-mode replacement compensates secret state.

Aivo must discover supported built-in, process, local-service, external-service, and static extensions from the Manifest/API v2 language-neutral contract without executing untrusted code; every other version pair, including v1, is rejected without fallback or automatic conversion. The legacy `aivo.plugin.json` and `.aivo-plugin/plugin.json` package formats, JSONL plugin process runtime, plugin RPCs, and plugin tool/hook/provider contribution paths are unsupported and are never discovered, started, adapted, or exposed. Trust, source enablement, readiness, global per-tool visibility, eligibility, conversation activation, authorization, and execution are distinct states. Before the first primary model request, the Host prepares a bounded eligible resource catalog across imported Skills, Manifest v2 extensions, and MCP adapters; globally disabled sources and globally hidden exact tools are excluded before the auxiliary resolver sees one Host-owned candidate for each eligible MCP/extension source. MCP source and concrete-tool metadata used by this Host-only catalog is independent of Agent-visible executors: the primary Agent receives no general MCP source-enumeration tool and sees only concrete MCP tools selected for its task. The primary Agent always receives `tool_resolve` and may call it with a concise missing capability; the Host then invokes the same bounded auxiliary source-group selection over current eligible candidates, expands validated groups locally, and atomically replaces the conversation's complete concrete automatic tool set for the next model step. Replacement does not accumulate, create warm leases, or alter manually activated tools. An immediate submit may additionally carry chooser-selected typed Skill, extension, or MCP source IDs. Core revalidates them against the same current catalog, merges an enabled Skill into that conversation's active instructions, and expands an enabled extension/MCP source only to its currently registered globally visible tools. The Host—not the auxiliary model—injects canonical summaries for selected Skills, loads full Skill instructions only for that validated subset, injects selected extension context, and freezes exact selected tool registration and schema identities in a Tool Snapshot assembled from eligible core primitives, `tool_resolve`, the conversation's manual set, its current automatic set, and separately authorized mode controls. Catalog preparation may establish readiness or refresh an already enabled source, but selection cannot install, import, trust, enable, bind credentials, authorize, or execute a tool. Skill/context selection remains request-scoped, while manual and automatic tool sets belong only to their conversation. Global visibility changes affect future automatic/manual selection and do not revoke an existing conversation selection. Every executable canonical tool name is an ASCII `_`/`-`-namespaced identifier matching the global Provider-safe contract before registration. Manifest v2 rejects invalid contributed names; generated MCP adapter names follow the same rule while retaining the upstream MCP name separately for execution. The same canonical name remains authoritative through catalogs, activation, Tool Snapshots, Provider declarations and history, returned calls, permission evaluation, execution, UI emission, and persistence; collisions are rejected and no Provider wire alias exists. Tool-group auxiliary selection receives only the intent and sanitized source-group name/description lines and cannot author membership or injected summary content. Extension processes, streams, calls, services, artifacts, and views have bounded output/backpressure, cancellation, draining, restart/update behavior, and deterministic teardown. A supervised local service may retain a fixed loopback URL or use a versioned bounded readiness handshake after binding an operating-system-assigned loopback port; the Host validates the announced root HTTP origin, owns the bearer and current-generation endpoint, and rejects timeout, overflow, malformed, non-loopback, or stale endpoints before readiness. For an extension tool associated through Manifest v2 `views[].tools`, the Host may add a bounded immutable view reference to the tool's UI details, preferring a declared `tool-detail` surface and using `page` only as a fallback; extension-returned data cannot select another extension, view, route, or Host surface. Complex extension Web views use isolated Host surfaces without Node integration, privileged preload access, ambient credentials, or unrestricted navigation, including when their Web contents is embedded into the main window's contextual inspector. An embedded View is mount-identified by its Host-resolved extension, View, and surface; when only the selected tool-call context changes, Electron main retains that isolated WebContents, replaces only the bounded Host context with a monotonic revision, and notifies the page through the versioned bridge. Stale mounts and context updates cannot retarget another View or change its origin, backend, token, actions, route, or surface.

An MCP source may capture a bounded non-secret functional description and stores an omitted description as empty. For an existing source, its edit surface may explicitly ask the configured auxiliary model to draft that description from every current stored discovered tool name and description. Core sends no endpoint, command, arguments, environment, headers, roots, authentication data, credential references, or executable tools, treats tool text as untrusted data, and returns bounded plain text that replaces only the unsaved description draft. A missing auxiliary model, empty tool catalog, catalog that cannot represent every member within Host bounds, cancellation, or Provider failure is actionable and does not infer, save, probe, start, or mutate the source. Every executable extension uses its validated Manifest name and available description. Automatic auxiliary selection presents one stable group name and optional description per eligible source instead of its concrete members; selecting a group expands to all current eligible members locally. Global per-tool hiding remains authoritative during expansion, and a source with no description remains an automatic-selection candidate with a blank description value.

Acceptance: `AT-EXTENSION-001` covers strict Manifest/API v2 and Protocol v1 validation, v1 and mixed-version rejection, legacy plugin format/RPC/process/catalog refusal, global name characters and length, all extension runtime types, trust and lifecycle transitions, static/dynamic catalog preparation, fixed and dynamically announced loopback service behavior, readiness handshake bounds/origin refusal/current-generation routing, request-scoped canonical Skill summary and validated instruction/context injection, MCP functional descriptions including complete safe tool-catalog generation and draft-only non-mutation, one candidate per MCP/extension, complete eligible group expansion, session manual/automatic isolation, initial and Agent-requested bounded automatic-set replacement, registration collision refusal and unchanged Provider identity, schema drift, immutable Tool Snapshots, MCP adaptation with separate upstream names, partial catalog failure and recovery, process/service failure and recovery, Host-derived tool view references, isolated standalone and embedded Web surfaces, mount-scoped revisioned context update/reuse and stale-update refusal, credential binding, update/removal, deterministic identity-change teardown/reopen, inert legacy plugin records, and historical fallback behavior.

Direct MCP credential acceptance: `AT-EXTENSION-001` additionally covers environment-reference and direct secure-store-reference Bearer resolution, direct-credential preservation/replacement/compensation, and reference-only persistence and output. `CT-SECURITY-001` and `CT-RELIABILITY-001` cover write-only transport, non-return, cleanup, repetition, and failure recovery.

### REQ-EXTENSION-002 Conversational MCP source registration

Aivo must let a coding Agent translate an explicit user request into an exact, bounded proposal to register one supported MCP source without mutating durable state, connecting to a remote endpoint, or starting a process. The trusted built-in contributes only this registration-proposal executor and does not expose a general MCP source-listing executor to the primary Agent. The proposal uses a Provider-safe Host-owned namespaced tool, contains configuration and Host credential references rather than raw secrets, is immutable, short-lived, single-use, and owned by the originating session and turn. The model and auxiliary resolver cannot approve, trust, bind credentials, persist, enable, connect to, start, or execute the source. A privileged native confirmation bound to the exact proposal is required before the Host independently revalidates it, saves the source disabled, performs bounded cancellable capability discovery, rejects invalid identities and collisions, and marks it ready and enabled only after success. Failure leaves no partial eligible tools. A ready enabled source is durable global installation state and becomes eligible in later conversations through the existing bounded pre-call resolver and immutable Tool Snapshot; registration does not create, copy, or change another conversation's manual active-tool state.

Acceptance: `AT-EXTENSION-002` covers absence of a general Agent-visible MCP source-listing executor, conversational proposal construction, safe proposal summaries, exact native confirmation, validation, denial, expiry, replay and concurrency refusal, no pre-confirmation process or connection, secret-reference isolation, disabled-first persistence, probe success/failure/timeout/cancellation, collision handling, retry and cleanup, restart persistence, later-conversation eligibility, and continued session isolation.

### REQ-EXTENSION-003 Chrome-style extension runtime messaging

Aivo must provide an Aivo-native Chrome-style runtime message boundary for trusted enabled service extensions without claiming or loading arbitrary Chrome extensions. The Host accepts only Manifest/API v2; v1 and mixed version pairs fail discovery without fallback. A v2 service opts in with the exact `runtime.messaging` permission. A registered isolated extension View may send one bounded JSON request to its own current Host-resolved service generation and may open a bounded named long-lived Port that carries ordered bounded JSON events and messages. Electron main owns sender and extension/View identity validation, fixed well-known endpoint routing, bearer injection, timeouts, connection limits, backpressure, and deterministic cancellation; the View never receives backend origins, credentials, arbitrary Aivo RPC, cross-extension routing, or installation/trust/tool authority. Same-identity Agent calls retain the View and its Ports while context and service events update content without navigation. View close, identity change, service EOF/failure/stop, renderer loss, and explicit disconnect close every owned Port exactly once.

Acceptance: `AT-EXTENSION-003` covers strict Manifest/API v2 validation, v1 and mixed-version refusal, permission validation, bounded one-shot request/response, named Port open/message/event/disconnect behavior, ordering, repeated calls without navigation, unsupported-page bridge refusal, and refusal of stale, cross-extension, oversized, malformed, timed-out, stopped, or excess-connection operations. `CT-SECURITY-001` and `CT-RELIABILITY-001` cover credential isolation, sender ownership, payload bounds, backpressure, cancellation, EOF, repeated disconnect, and deterministic teardown.

### REQ-EXTENSION-004 Visual local extension installation

Aivo must let a user install and manage a local Manifest/API v2 extension entirely through the desktop UI without typing a path, command, or RPC sequence. Electron owns native directory selection. Core performs a non-executing bounded preview that validates the source package and returns its safe identity, runtime, contributions, declared permissions/requirements, canonical source path, and complete integrity. Installation requires explicit native confirmation bound to that exact path and integrity. Core revalidates the source, copies it into private Aivo-managed integrity-addressed storage beneath the platform application-data `Aivo/Default/Extensions` hierarchy, reloads the copied package, requires the same integrity, and atomically publishes it before trust, optional enablement, and durable persistence. Executable extensions must be described as running with the user's OS authority rather than as sandboxed. Runtime and restart restoration use only the managed copy, so later source edits, moves, or deletion have no effect. Models and extension content cannot install or trust. Disable deterministically stops owned runtime state without deleting the package; uninstall stops runtime and deletes only the Aivo-managed copy and record while preserving the selected source.

Acceptance: `AT-EXTENSION-004` covers native selection, non-executing preview, bounded metadata, explicit executable warning, exact integrity confirmation, verified staged copy, atomic install/update, list/enable/disable/uninstall, source independence, restart restoration, schema v3 linked-row promotion, no model authority, source-file preservation, and empty/loading/error/success/narrow UI states. `CT-SECURITY-001` covers source/copy TOCTOU refusal, path containment, symlink refusal, renderer/model/extension denial, managed-path privacy, deletion scope, trust binding, and authority wording. `CT-RELIABILITY-001` covers schema v3-to-v4 backup/transaction/idempotence, downgrade restoration, staging/publication failure, abandoned cleanup, startup failure, repeated operations, and deterministic teardown.

### REQ-WORKTREE-001 Worktree and parallel work lifecycle

Aivo must create, associate, inspect, and clean up task worktrees and parallel agent activity with a visible owner and without deleting user work implicitly.

Acceptance: `AT-WORKTREE-001` covers worktree service ownership and parallel agent behavior.

### NFR-SECURITY-001 Secret and privilege isolation

Provider credentials, OAuth tokens, authorization headers, signing material, and other secrets must remain in privileged local services or approved secure storage. They must not enter renderer persistence, logs, crash output, analytics, committed fixtures, or user-visible diagnostics.

Acceptance: `CT-SECURITY-001` combines targeted credential/redaction tests with repository secret review.

### NFR-RELIABILITY-001 Lifecycle and data recovery

Long-running calls, goroutines, streams, terminals, subprocesses, MCP/LSP clients, worktrees, and pending user interactions must have an owner, cancellation path, bounded output/backpressure, deterministic teardown, and actionable failure state. Cancellation must not leak executable intent, approvals, or questions into a later turn. Persistence changes must be transactional and recoverable from a pre-migration backup.

Acceptance: `CT-RELIABILITY-001` covers runtime cancellation/cleanup, cross-turn isolation, pending-interaction teardown, and migration failure/rollback evidence when schema changes apply.

### NFR-UI-001 Responsive and complete states

Desktop layouts must support content-driven wide and narrow sizes, keyboard/focus behavior, scrolling and overflow, and loading, empty, error, long-content, cancellation, and permission states without modifying generated routes or shared primitives under `apps/desktop/src/components/ui`.

Acceptance: `AT-UI-001` combines lint/build with wide/narrow screenshots and focused manual acceptance for changed flows.

### NFR-UI-002 Desktop visual scale and theme

The desktop renderer must use a shared, semantic typography and control scale grounded in Apple HIG logical reference dimensions while remaining usable across the supported macOS, Windows, and Linux Electron targets. The theme must preserve readable hierarchy, compact pointer-oriented controls, semantic light/dark colors, visible keyboard focus, and responsive reflow without modifying generated routes or shared primitives under `apps/desktop/src/components/ui`.

Acceptance: `AT-UI-002` combines theme-token inspection, lint/build, representative wide/narrow screenshots, overflow checks, and focused keyboard/primary-action acceptance.

### NFR-OBSERVABILITY-001 Safe operation diagnostics

Important backend operations must emit structured start, completion, cancellation, and failure information with an operation ID, duration, and safe dependency/error classification. Logs and diagnostics must exclude secrets and raw sensitive prompt or tool content.

Acceptance: `CT-OBSERVABILITY-001` covers structured event fields and redaction behavior.
