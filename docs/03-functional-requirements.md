# Aivo functional requirements

Each section owns one stable behavior. IDs are never reused; replaced or removed requirements remain with a status marker.

### REQ-PROVIDER-001 Provider configuration and health

Aivo must let the user configure and inspect supported provider accounts, resolve an available model, surface actionable authentication or dependency errors, and run provider diagnostics without placing credentials in renderer state or logs. After initialization, desktop settings must read configured Providers from the Core catalog, let the user refresh Aivo's shared Provider/model ecosystem catalog for subsequent add-Provider model selection, refresh an individual configured Provider's remote model list, add or connect one through the same connection flow used during initialization, and remove a whole Provider configuration only after explicit confirmation through the Core-owned deletion operation. A successful ecosystem refresh must replace the local public catalog cache and immediately reload the settings catalog. Ecosystem Providers whose recognized protocol has a compatible remote model-list operation must expose configured-Provider refresh; unsupported static protocols must explain the catalog-refresh alternative when invoked. A successful configured-Provider refresh must replace only that Provider's cached list and displayed list-default model through Core-owned persisted configuration and credentials. Neither refresh changes the application's active model preference; remote endpoint, authentication, and parsing failures remain actionable and preserve the previous catalog. Every local executable tool identity must already match the global `^[A-Za-z0-9_-]+$` Provider-safe contract with a 64-byte maximum before it enters a Provider request. Provider adapters must serialize and observe that exact canonical identity without encoding, decoding, escaping, or alias lookup.

Acceptance: `AT-PROVIDER-001` covers provider registry/configuration behavior, settings catalog/ecosystem-refresh/configured-provider-refresh/add/connect/confirmed-delete states, public catalog cache replacement, immediate add-flow model availability, persisted-config remote model refresh with per-Provider cache/default-list replacement, active-preference preservation, unchanged canonical tool names across declarations, history, final responses, and streams, plus the provider smoke path. `AT-UI-001` covers the settings loading, empty, error, busy, wide, and narrow states.

### REQ-PROJECT-001 Local project context

Aivo must let the user add or open a local project, maintain project-scoped runtime configuration, and isolate conversation, tool, worktree, and discovery context between projects.

Acceptance: `AT-PROJECT-001` covers project service and isolation behavior.

### REQ-PROJECT-002 Initial workspace for unscoped conversations

Aivo must present one local default directory during initialization, let the user accept it or select another directory, and persist the confirmed path before initialization completes. Aivo uses that same directory as the coding context for every temporary or otherwise projectless conversation. These conversations remain unscoped in project navigation. Aivo must not create per-conversation directories or silently switch a confirmed path. If the configured root is missing, Aivo recreates that exact root; an unconfigured path, a non-directory at that path, or a creation failure produces an actionable error without changing explicitly selected project behavior.

Acceptance: `AT-PROJECT-002` covers default-path presentation and confirmation, initialization validation, repeated unscoped conversation creation against one directory, exact-root recreation, explicit-project precedence, non-directory refusal, and absence of per-conversation directory creation.

### REQ-PROJECT-003 Agent project catalog and immutable session binding

Aivo must provide a trusted namespaced built-in extension that lets an eligible Agent query the bounded local project catalog, register an existing absolute local directory without creating or cloning content, and bind only its current unscoped coding conversation to an exact returned project. A renderer chooser may request the same binding by submitting the exact existing project ID and displayed root path as a typed resource reference; handwritten prompt text cannot bind a project. Project query is read-only; registration and association follow the active permission mode and identify the exact target. A conversation's first project association atomically updates its durable project ownership and coding context. The same association is idempotent, while switching, detaching, arbitrary-session mutation, association from a specialized workspace, and association with live interactive terminals are refused. After association, the next model request and desktop state use the bound project's workspace-dependent context without adding another unqualified core tool.

Acceptance: `AT-PROJECT-003` covers bounded query/pagination, existing-directory registration, hidden restoration, permission behavior, immutable and concurrent association, failure rollback, workspace refresh, and desktop project-state presentation.

### REQ-AGENT-001 Dynamic Agent mode management

Aivo must present exactly one visible code-owned built-in Agent, Assistant, as the composer and new-session default, while retaining only runtime-required summary, title, and scheduler workers as hidden built-ins. The “Extensions and MCP” management surface lets the user search, inspect, create, edit, reset, and delete supported definitions through Core-owned typed operations. Assistant appears without being eagerly copied into persistence; editing it creates a durable validated override, and resetting it removes only that override and restores the code default. Removed legacy built-in identifiers are not listed or manageable and resolve to Assistant only when encountered in historical sessions. A user-created global mode is durable and may be deleted only when no session or another managed mode references it. Hidden workers remain code-owned and unavailable to management. Core validates stable lowercase identifiers, display metadata, prompt, optional model and sampling settings, maximum steps, permission scope, primary/subagent role, and at most 16 unique associated subagent IDs before persistence and again before execution. Agent creation and editing must present eligible targets through a keyboard-operable multi-select dropdown; only primary-capable modes may own associations, and every target must be an existing visible subagent-capable non-self mode. Global management DTOs and stored definitions do not contain toolsets: Assistant retains its code-owned capability set and custom global modes receive the safe runtime default. Effective resolution applies code defaults, then durable global definitions, then existing project runtime configuration; project files remain project-scoped, may retain project-specific toolset policy and replace subagent associations, and are never rewritten by global CRUD. Successful changes are reflected by subsequent global/project catalog reads and conversation Agent pickers without an application restart.

Acceptance: `AT-AGENT-001` covers the single visible built-in Assistant default and retired-ID fallback, hidden worker protection, Assistant origin/reset, custom create/read/update/delete, persistence/restart, bounds and protected-ID refusal, session/association referenced-mode deletion and role-change refusal, toolset omission plus built-in/safe runtime capability restoration, effective global/project precedence, runtime prompt/model/tool/permission/association application, typed RPC behavior, search/editor states, and conversation-picker refresh.

### REQ-PROMPT-001 Validated prompt management

Aivo must provide a global Core-owned catalog for categorized Agent, protocol, auxiliary, task, dynamic-context, and quick prompts. Built-in defaults are embedded `aivo.prompt/v1` Markdown; bounded symlink-free managed files may override them. Core validates identity, category, policy, size, variables, required references, and complete rendering before an override can become active. Invalid working content remains visible with actionable diagnostics but the next execution uses the last validated revision or embedded default. One execution retains one immutable prompt snapshot. Required prompts may be edited and reset but not disabled or deleted; optional built-ins may be disabled; only bound custom Agent and quick prompts may be created and deleted subject to reference checks. Tool and parameter descriptions are inspectable but read-only. The associated-subagent explanation is not a managed protocol prompt: Core deterministically generates it from the effective validated Agent association list and omits it when that list is empty. Renderer management uses typed Core operations and cannot make prompt text authoritative for tools, permissions, credentials, structured envelopes, delegation targets, or execution. Global edits apply to later executions without restart; project instructions, Skills, extension context, MCP Prompts, and project runtime overlays remain independent and higher-precedence where already specified.

Acceptance: `AT-PROMPT-001` covers embedded catalog integrity, parsing and bounds, variable and reference validation, atomic save/reload, last-known-good restart recovery, required/optional/custom lifecycle, immutable execution snapshots, consumer rendering, Agent reference migration and compatibility, typed RPC behavior, top-bar routing, responsive editor states, external manual reload, and quick-prompt refresh.

### REQ-SESSION-001 Conversation and task execution

Aivo must let the user create or continue a conversation, submit a task, receive streaming progress, cancel execution, and recover or retry after an actionable failure without corrupting prior history. Immediate message submission may carry a bounded typed set of chooser-selected resource IDs; Core validates the entire set before event/turn creation and merges valid Skill/tool/source selections into only that conversation. Each conversation owns an independent manual tool set and one automatic tool set. Manual activation and explicit core-tool disablement remain until changed by the user. Before the first primary request, auxiliary selection classifies whether the user is inspecting available capabilities or needs to use them: inspection initializes an empty durable automatic set but exposes the complete eligible concrete catalog to that one Provider request without a Host-owned expanded-tool count cap, while use persists the complete concrete expansion of the selected groups as the stable automatic set. The automatic set then remains stable until the primary Agent explicitly requests a successful persistent replacement through the Host tool-selection control. Replacement never adds to or removes from the manual set. A selection made before a conversation exists is consumed by the next created conversation exactly once and is not a global default. Queued or steered input cannot carry resource references. A primary-capable mode with associated subagents may let the model autonomously call the existing bounded delegation tool only for those effective target IDs; a mode with no associations receives no delegation tool, and every call is revalidated before a child session is created. Delegation is task-driven rather than unconditional fan-out and retains existing depth, parallelism, cancellation, permission, result-order, and child-session lifecycle rules. Cancelling a turn keeps its user-visible history but terminalizes its owned execution and interactions; later model requests must not treat the cancelled turn's instructions or approvals as active work.

For each settled successful primary model request, Core must persist a bounded runtime summary without prompt, response, tool, credential, or raw Provider data. The summary owns one LLM step, request wall time, available first-token/decode timing, normalized Provider-reported input and output token counts, and cache-read counts together with whether the Provider actually supplied cache accounting. The desktop conversation must aggregate those persisted summaries into completed-turn and step counts, summed LLM duration, sampled average first-token latency and decode throughput, cache-hit percentage only across wholly cache-accounted input, and input/output totals beside the active composer. Unsupported readings and historical events without summaries are omitted rather than estimated, and no statistic is transmitted as remote telemetry.

Core must automatically compact settled model-visible conversation history when its safe estimated pressure reaches the configured percentage of the selected model's advertised context length, defaulting to 80%, while falling back to the existing conservative local capacity when model metadata is unavailable. Compaction preserves a bounded recent tail verbatim, consolidates older context into one durable summary, retains original events for user-visible history and recovery, and sends only the latest summary plus post-boundary messages in later Provider requests. The newest unanswered user request is never hidden by automatic compaction. Manual compaction uses the same bounded Core operation, requires an idle session, is cancellation-aware, and exposes only safe status/summary identifiers in its visible system note.

For automatic selection, the auxiliary model can select only an exact typed MCP or non-built-in extension source ID; it never selects concrete member names, generated Provider namespaces, standalone tools, or Skills. The Host expands a selected source locally to every currently registered, mode-eligible, globally visible concrete member. For use intent, every expanded canonical name—not the source ID—becomes the stable conversation automatic set and immutable Tool Snapshot membership; later source-catalog changes do not silently alter it. For inspection intent, the Host injects the complete eligible concrete catalog without a count cap, marks the durable automatic set initialized but empty, and freezes those names only in the first request's Tool Snapshot. The visible result contains only categorized extension/MCP/tool/skill resource summaries: each MCP/extension source appears once with its exact ID and injected member count, while concrete names remain internal to session state and the snapshot.

Acceptance: `AT-SESSION-001` covers session runtime, turn, streaming, cancellation, recovery, persisted successful-step timing/usage normalization and aggregation, malformed or unavailable metric omission, session-scoped and one-shot draft tool activation, request-only complete inspection injection, conversation-persistent use selection, source-group expansion and snapshot stability, one-event live initial-selection loading/result transitions, association-narrowed model delegation and forged/stale target refusal, pending-interaction cleanup, and isolation of a cancelled turn from the next model request.

### REQ-WORKSPACE-001 Sidebarless chat workspace

The desktop project chat workspace must prioritize the active conversation without reserving persistent left, right, or bottom panels. New conversation, history, project context, extensions, settings, model, permission, agent-mode, attachment, microphone, and submit entry points must remain reachable through compact top-level or composer controls, while conversation and permission/question states preserve responsive layout and visible keyboard focus. Typing `@` at the composer caret opens a local, fuzzy-searchable mention chooser containing existing projects plus only globally enabled imported Skills, installed extensions, configured MCP sources, and built-in tools. The chooser also exposes local “选择文件或文件夹” and “压缩上下文” actions. The compaction action consumes the query, invokes the existing idle-session Core compaction operation, provides bounded success/failure feedback, and creates neither submitted prompt text nor a typed resource reference. On macOS the file action consumes the active `@` query and directly opens one native file-or-directory chooser without an intermediate type confirmation; a selected file enters the existing attachment flow, while a selected directory enters the existing project-context flow. The action does not create a typed resource reference itself, and equivalent Windows/Linux combined-selection behavior remains subject to platform acceptance. The current project is identified and ordered first. Each extension and MCP source appears once at source level; their contributed tools are not expanded or duplicated under the tool group. Choosing a resource consumes the active `@` query, renders a visible removable resource tag inside the composer editing region, and records its typed stable identity; repeated selection is deduplicated and only one project tag may remain selected. On immediate submit, Core revalidates the selection and attaches the exact project, Skill, built-in tool, or source-level extension/MCP capabilities to that conversation; handwritten lookalike text has no binding effect. A project may initialize or bind an unscoped conversation but cannot switch an existing binding, while other resource selections merge with existing conversation activation and cannot override global disablement. Persistent or top-bar-triggered standalone right activity panels and bottom terminal panels, their resize handles, and their top-bar triggers are not mounted in this workspace; a user-opened contextual inspector governed by `REQ-TOOL-002` may temporarily share the chat width.

Acceptance: `AT-WORKSPACE-001` combines lint/build with wide and narrow screenshots plus focused acceptance for navigation reachability, composer controls, `@` chooser filtering, keyboard selection/dismissal, the combined file-or-folder local action, typed selection transport, scrolling, overflow, absence of auxiliary panel chrome, and empty/conversation states.

### REQ-TOOL-001 Controlled local tool execution

Aivo must expose exactly the unqualified `read`, `bash`, `edit`, and `write` execution primitives to a default coding Agent in stable order, plus the Host-owned `tool_resolve` control that replaces the conversation's automatic tool set when the Agent identifies a concrete missing capability. Registered tools default to globally visible for future selection; the user may globally hide or restore an exact canonical tool. A globally hidden tool remains manageable but is excluded from new conversation choices, typed resource references, and auxiliary candidates; it is not retroactively removed from a conversation that already selected it. The user may separately disable or restore an eligible core tool for one conversation (or the one pending new conversation); selecting an eligible built-in tool through the composer mention chooser merges it into the same conversation's manual set. An explicitly disabled core tool is omitted from that conversation's Provider request and Tool Snapshot, while missing global and session preference state retains all four defaults. The four primitives share one active Execution Environment and retain validated inputs, explicit permission policy, bounded model output, cancellation, deterministic cleanup, and safe recorded results. Workspace file paths supplied to `read`, `edit`, and `write` are relative to the active workspace root; only an exact retained-output reference returned by the Host may be absolute for `read`. `read` reads one bounded text or supported image file; `bash` runs one foreground non-interactive Bash command; `edit` atomically applies one batch of exact, unique, non-overlapping replacements against one original file snapshot; and `write` atomically creates or completely overwrites one text file. `apply_patch` and specialized file, Git, test, build, formatting, diagnostic, terminal, LSP, web, automation, and sub-Agent executors are not default execution tools and have no execution aliases. Workspace policy and confirmation are correctness controls, not process containment; the active local or external Execution Environment owns actual authority and isolation.

The auxiliary tool selector receives only the user intent plus bounded single-line `kind:id：description` entries for eligible MCP and non-built-in extension sources. When an MCP functional description is blank, the Host assembles every current eligible tool name and description as its bounded fallback; a blank extension Manifest description stays blank. Descriptions are untrusted data. Its only valid response is a strict JSON object containing an exact `intent` classification of `inspect` or `use` and a unique `sources` array of exact `{kind,id}` MCP/extension identities. Concrete tool names and the `tool`/`skill` kinds are invalid selector output. Every eligible standalone `tool` bypasses source selection and remains injected as itself; MCP adapters retain their exact server ID as Registry source identity. `inspect` requires an empty source array and makes the Host inject the complete eligible catalog for one request; `use` persists every member of the validated source expansions. The Host owns classification, membership, eligibility, schemas, Provider serialization, lifetime, and snapshot assembly. The visible initial-selection note contains only bounded state, typed source/tool/skill summaries, member counts, and lifetime—never concrete MCP/extension member names or selector internals. `tool_resolve` is use-only and persistent.

Acceptance: `AT-TOOL-001` covers the exact registry and schemas including default and explicitly disabled core-tool surfaces, strict inspect/use classification, source-group selection and uncapped concrete expansion, complete request-only inspection beyond the former 64-tool limit, persistent use selection, safe one-event live initial-selection recording, relative-path guidance, text/image reads, Bash output/artifacts/timeouts, exact atomic edit/write behavior, permission and environment boundaries, cancellation/cleanup including invalidation of turn-owned pending approvals, direct `apply_patch` removal, historical fallback rendering, and safe result recording.

### REQ-TOOL-002 Contextual tool activity inspector

The initial selection disclosure must identify `request` lifetime as a one-request temporary injection and `conversation` lifetime as a persistent automatic set. Its resource contract recognizes only extension, MCP, tool, and skill; Agent modes are configuration rather than injectable resources. Running and failed payloads do not require a lifetime; a completed payload with missing or unknown lifetime makes the typed payload malformed and retains the ordinary system-note fallback.

The desktop conversation must present the Host's typed initial automatic-tool selection note as an accessible disclosure before later tool activity. It is collapsed by default, keeps its current state summary visible while the auxiliary selector is running or after it settles, and updates the same row in place to resource-level groups or an explicit empty/failure state available by expanding the disclosure. Extension and MCP sources appear once under their category with exact source ID/display name and concrete member count; standalone tools and Skills use their own categories. The renderer merges live note changes by event identity, still loads the final persisted result from history, and falls back to the ordinary system-note rendering when the typed payload is malformed. The desktop conversation must present every visible tool call as an accessible label containing the tool's name, arranged from left to right in a compact wrapping activity region without interleaved execution-description text. Activating any label or the surrounding activity region must open the same contextual right-side inspector for that complete activity, not a single-label view. The inspector must automatically open when a new tool call is received in an active conversation, without opening merely because historical calls were loaded. Manually closing it suppresses further automatic opening for that conversation while preserving manual label activation; a different or newly created conversation resets that suppression. The inspector must animate into the chat layout and present every tool call in the activity as one timeline ordered by call time, using an associated invocation description as the first applicable item title only when that description exists; immediately following calls with the same description must not repeat it, and calls without an invocation description must not render a title. Every item shows the tool name as supporting text alongside execution status. Each timeline item must open and dismiss an overlapping in-panel detail view. When a tool call carries a Host-derived reference to an associated isolated extension `tool-detail` view, or to a tool-associated `page` fallback, that Web page must become the overlapping detail view automatically. A newly selected call with the same Host-resolved extension ID, View ID, and surface must reuse the mounted isolated WebContents and receive a bounded latest-wins context update without navigation or a loading fallback; changing View identity or closing the detail tears it down, and reopening recreates it. Unavailable views must retain the native bounded detail fallback. The inspector must not reintroduce a persistent auxiliary workspace or terminal panel and must preserve responsive layout, keyboard focus, safe result rendering, and live status updates.

Acceptance: `AT-TOOL-002` combines focused initial-selection parsing/live-update merging, timeline-title, and same-identity View-reuse regression coverage, lint/build, and wide and narrow interaction screenshots covering the default-collapsed loading-to-result selection disclosure, its visible summary, and expandable empty/failure/fallback states, per-tool naming, left-to-right wrapping, omission of interleaved execution descriptions, non-repeating consecutive invocation descriptions, omitted titles for calls without descriptions, label and activity-region activation, complete activity coverage, call-time ordering and status, live-call automatic opening, historical-load non-opening, per-conversation manual-close suppression and reset, push-open/close animation, stacked native and extension Web detail navigation, same-identity context switching without reload, different-identity and close teardown/reopen/fallback, long and missing content, repeated selection, and running, approval, success, and failure states.

### REQ-EXTENSION-001 Skills, plugins, and MCP

Initial tool-group auxiliary selection must distinguish `inspect` from `use`. Inspection exposes the complete currently eligible concrete catalog to exactly one primary Provider request without a Host-owned concrete-tool count cap, persists no automatic names, and initializes an empty durable automatic set; use persists every member of validated typed MCP/extension source IDs. Later `tool_resolve` selection is always use-only and conversation-persistent. Request-only inspection tools participate in only that request's immutable Tool Snapshot and retain all global visibility, readiness, mode, registration, permission, and stale-call checks. The strict auxiliary decision contains only classification and exact source identities; the Host owns expansion, membership, lifetime, and categorized visible summaries.

The desktop MCP settings flow must support both environment-reference Bearer authentication and one-time direct Bearer-token entry. Direct values cross only the privileged save boundary, become Host-owned secure-store references immediately, are never returned or prefilled, and are absent from SQLite, renderer persistence, catalogs, logs, and diagnostics. Saving without a replacement preserves an existing reference, while failed save or authentication-mode replacement compensates secret state.

Aivo must discover supported built-in, process, local-service, external-service, and static extensions from the Manifest/API v2 language-neutral contract without executing untrusted code; every other version pair, including v1, is rejected without fallback or automatic conversion. The legacy `aivo.plugin.json` and `.aivo-plugin/plugin.json` package formats, JSONL plugin process runtime, plugin RPCs, and plugin tool/hook/provider contribution paths are unsupported and are never discovered, started, adapted, or exposed. Trust, source enablement, readiness, global per-tool visibility, eligibility, conversation activation, authorization, and execution are distinct states. Before the first primary model request, the Host prepares a bounded eligible resource catalog across imported Skills, Manifest v2 extensions, and MCP adapters; globally disabled sources and globally hidden exact tools are excluded before the auxiliary resolver sees one Host-owned candidate for each eligible MCP/extension source. MCP source and concrete-tool metadata used by this Host-only catalog is independent of Agent-visible executors: the primary Agent receives no general MCP source-enumeration tool and sees only concrete MCP tools selected for its task. The primary Agent always receives `tool_resolve` and may call it with a concise missing capability; the Host then invokes the same bounded auxiliary source-group selection over current eligible candidates, expands validated groups locally, and atomically replaces the conversation's complete concrete automatic tool set for the next model step. Replacement does not accumulate, create warm leases, or alter manually activated tools. An immediate submit may additionally carry chooser-selected typed Skill, extension, or MCP source IDs. Core revalidates them against the same current catalog, merges an enabled Skill into that conversation's active instructions, and expands an enabled extension/MCP source only to its currently registered globally visible tools. The Host—not the auxiliary model—injects canonical summaries for selected Skills, loads full Skill instructions only for that validated subset, injects selected extension context, and freezes exact selected tool registration and schema identities in a Tool Snapshot assembled from eligible core primitives, `tool_resolve`, the conversation's manual set, its current automatic set, and separately authorized mode controls. Catalog preparation may establish readiness or refresh an already enabled source, but selection cannot install, import, trust, enable, bind credentials, authorize, or execute a tool. Skill/context selection remains request-scoped, while manual and automatic tool sets belong only to their conversation. Global visibility changes affect future automatic/manual selection and do not revoke an existing conversation selection. Every executable canonical tool name is an ASCII `_`/`-`-namespaced identifier matching the global Provider-safe contract before registration. Manifest v2 rejects invalid contributed names; generated MCP adapter names follow the same rule while retaining the upstream MCP name separately for execution. The same canonical name remains authoritative through catalogs, activation, Tool Snapshots, Provider declarations and history, returned calls, permission evaluation, execution, UI emission, and persistence; collisions are rejected and no Provider wire alias exists. Tool-group auxiliary selection receives only the intent and sanitized source-group name/description lines and cannot author membership or injected summary content. Extension processes, streams, calls, services, artifacts, and views have bounded output/backpressure, cancellation, draining, restart/update behavior, and deterministic teardown. A supervised local service may retain a fixed loopback URL or use a versioned bounded readiness handshake after binding an operating-system-assigned loopback port; the Host validates the announced root HTTP origin, owns the bearer and current-generation endpoint, and rejects timeout, overflow, malformed, non-loopback, or stale endpoints before readiness. For an extension tool associated through Manifest v2 `views[].tools`, the Host may add a bounded immutable view reference to the tool's UI details, preferring a declared `tool-detail` surface and using `page` only as a fallback; extension-returned data cannot select another extension, view, route, or Host surface. Complex extension Web views use isolated Host surfaces without Node integration, privileged preload access, ambient credentials, or unrestricted navigation, including when their Web contents is embedded into the main window's contextual inspector. An embedded View is mount-identified by its Host-resolved extension, View, and surface; when only the selected tool-call context changes, Electron main retains that isolated WebContents, replaces only the bounded Host context with a monotonic revision, and notifies the page through the versioned bridge. Stale mounts and context updates cannot retarget another View or change its origin, backend, token, actions, route, or surface.

An MCP source may capture a bounded non-secret functional description and stores an omitted description as empty. For an existing source, its edit surface may explicitly ask the configured auxiliary model to draft that description from every current stored discovered tool name and description. Core sends no endpoint, command, arguments, environment, headers, roots, authentication data, credential references, or executable tools, treats tool text as untrusted data, and returns bounded plain text that replaces only the unsaved description draft. A missing auxiliary model, empty tool catalog, catalog that cannot represent every member within Host bounds, cancellation, or Provider failure is actionable and does not save, probe, start, or mutate the source. For automatic selection only, a blank stored MCP description is supplemented by a non-persisted deterministic assembly of every current eligible tool name and description. Every executable extension uses its validated Manifest description without fallback. Auxiliary selection presents one exact typed ID per eligible source and selecting it expands all current eligible members locally. Global per-tool hiding remains authoritative during expansion.

Resource management and selection surfaces use exactly four injectable categories: extensions, MCP, tools, and Skills. Agent modes remain manageable through a separate secondary management action but are not a fifth resource category. A built-in Aivo executor is a standalone tool resource even when it is implemented through the trusted Manifest runtime; an installed third-party extension or MCP source appears once and owns its complete contributed tool list.

Intent-scoped tool acceptance: `AT-EXTENSION-001` additionally covers request-only initial inspection, persistent initial use and Agent-requested replacement, complete eligible source expansion, and request/snapshot isolation.

### REQ-EXTENSION-002 Conversational MCP source registration

Aivo must let a coding Agent translate an explicit user request into an exact, bounded proposal to register one supported MCP source without mutating durable state, connecting to a remote endpoint, or starting a process. The trusted built-in contributes only this registration-proposal executor and does not expose a general MCP source-listing executor to the primary Agent. The proposal uses a Provider-safe Host-owned namespaced tool, contains configuration and Host credential references rather than raw secrets, is immutable, short-lived, single-use, and owned by the originating session and turn. The model and auxiliary resolver cannot approve, trust, bind credentials, persist, enable, connect to, start, or execute the source. A privileged native confirmation bound to the exact proposal is required before the Host independently revalidates it, saves the source disabled, performs bounded cancellable capability discovery, rejects invalid identities and collisions, and marks it ready and enabled only after success. Failure leaves no partial eligible tools. A ready enabled source is durable global installation state and becomes eligible in later conversations through the existing bounded pre-call resolver and immutable Tool Snapshot; registration does not create, copy, or change another conversation's manual active-tool state.

Acceptance: `AT-EXTENSION-002` covers absence of a general Agent-visible MCP source-listing executor, conversational proposal construction, safe proposal summaries, exact native confirmation, validation, denial, expiry, replay and concurrency refusal, no pre-confirmation process or connection, secret-reference isolation, disabled-first persistence, probe success/failure/timeout/cancellation, collision handling, retry and cleanup, restart persistence, later-conversation eligibility, and continued session isolation.

### REQ-EXTENSION-004 Visual local extension installation

Aivo must let a user install and manage a local Manifest/API v2 extension entirely through the desktop UI without typing a path, command, or RPC sequence. Electron owns native directory selection. Core performs a non-executing bounded preview that validates the source package and returns its safe identity, runtime, contributions, declared permissions/requirements, canonical source path, and complete integrity. Installation requires explicit native confirmation bound to that exact path and integrity. Core revalidates the source, copies it into private Aivo-managed integrity-addressed storage beneath the platform application-data `Aivo/Default/Extensions` hierarchy, reloads the copied package, requires the same integrity, and atomically publishes it before trust, optional enablement, and durable persistence. Executable extensions must be described as running with the user's OS authority rather than as sandboxed. Runtime and restart restoration use only the managed copy, so later source edits, moves, or deletion have no effect. Models and extension content cannot install or trust. Disable deterministically stops owned runtime state without deleting the package; uninstall stops runtime and deletes only the Aivo-managed copy and record while preserving the selected source.

Acceptance: `AT-EXTENSION-004` covers native selection, non-executing preview, bounded metadata, explicit executable warning, exact integrity confirmation, verified staged copy, atomic install/update, list/enable/disable/uninstall, source independence, restart restoration, schema v3 linked-row promotion, no model authority, source-file preservation, and empty/loading/error/success/narrow UI states. `CT-SECURITY-001` covers source/copy TOCTOU refusal, path containment, symlink refusal, renderer/model/extension denial, managed-path privacy, deletion scope, trust binding, and authority wording. `CT-RELIABILITY-001` covers schema v3-to-v4 backup/transaction/idempotence, downgrade restoration, staging/publication failure, abandoned cleanup, startup failure, repeated operations, and deterministic teardown.

### NFR-RELEASE-001 Public source and release integrity

Aivo must publish licensor-owned source in a Public GitHub repository under `PolyForm-Noncommercial-1.0.0`, identify the project as source-available and noncommercial rather than OSI open source, preserve the Required Notice and commercial-authorization boundary, and keep every workspace package manifest private from accidental registry publication. The Public repository must start from the explicitly reviewed source snapshot, expose no superseded private repository refs, restore GitHub secret scanning, push protection, and private vulnerability reporting, and retain an external verified recovery bundle. A same-name Release record and `v<SemVer>` tag whose version matches all package manifests must trigger native macOS Apple Silicon, macOS Intel, Windows x64, and Linux x64 package and smoke gates. Successful publication must place normalized packages and a SHA-256 manifest in immutable Cloudflare R2 version paths before updating the stable channel manifest, then create or resume a GitHub Release containing the same digest-bound assets. Repetition may reuse byte-identical assets but must refuse missing digest metadata, conflicting bytes, incomplete platform builds, failed R2 readback, or absent signing evidence presented as a signed release.

Acceptance: `CT-LICENSE-001` covers canonical license text, source-available/noncommercial and commercial-authorization wording, Required Notice, and package metadata. `CT-RELEASE-001` covers tag/version/release-record binding, normalized platform assets, immutable R2 planning, stable manifest construction, conflicting or ambiguous artifact refusal, and a successful native tagged workflow. `CT-REPOSITORY-001` covers external backup, secret scan, new root history, new Public repository identity, absence of migrated refs, metadata, and repository security settings.

### NFR-RELIABILITY-001 Lifecycle and data recovery

Cancellation must not leak executable intent, approvals, or questions into a later turn. Persistence changes must be transactional and recoverable from a pre-migration backup.
