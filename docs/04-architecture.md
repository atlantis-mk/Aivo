# Aivo architecture

## Boundary model

```text
React routes and feature modules
        |
Electron preload and typed desktop services
        |
Versioned local HTTP contracts and event streams
        |
Go application services
        |
Domain models and ports
        |
SQLite, providers, OS processes, MCP, LSP, and other adapters
```

## Ownership and dependency rules

### Renderer

- Routes compose feature modules; generated route files do not own feature behavior.
- Shared primitives under `apps/desktop/src/components/ui` are read-only.
- Filesystem, process, credential, persistence, and OS access goes through typed preload services.
- Layout uses document flow, flex, and grid with explicit overflow before fixed or absolute positioning.

### Electron boundary

- Main and preload APIs are minimal, typed, capability-oriented, and validate renderer-provided paths and arguments.
- Packaged Electron spawns its bundled Core with an operating-system-assigned IPv4 loopback port and accepts the actual root origin only from a versioned, opt-in child readiness record. Main validates and health-checks that origin before creating the renderer, injects it through Host-authored preload startup configuration, and owns child teardown. The renderer CSP permits HTTP and WebSocket dynamic ports only on the exact IPv4 loopback host; it grants no endpoint-selection authority. Development may retain its fixed endpoint, but packaged startup never discovers or reuses a process on that port.
- Each process, stream, window, and subscription has explicit ownership, cancellation, and teardown.
- Generated bindings in `apps/desktop/bridge/go` are generated from their owner and never hand-edited.

### Desktop update boundary

- Electron main owns the fixed R2 stable-channel and GitHub Release metadata clients, stable SemVer comparison, platform/architecture artifact derivation, schema/origin/path validation, streaming download, SHA-256 verification, temporary package lifecycle, and OS package handoff.
- Preload exposes only state, check, download, install/handoff, cancellation, and state-subscription capabilities. Renderer data cannot select an update origin, URL, path, command, version, artifact, size, or digest.
- One coordinator owns at most one metadata or download operation. Every network request has a timeout and response bound, progress is bounded and throttled, shutdown aborts owned work, and partial or rejected files are removed.
- The updater requires matching R2 and same-tag non-draft GitHub Release asset metadata before download. Verification is defense in depth and does not replace platform signing, notarization, or OS security prompts.
- Installation is an explicit native-user handoff. macOS and Windows open the verified installer package; Linux reveals the verified AppImage rather than assuming an installation layout that Aivo does not own.

### Go core

- `core/domain` does not depend on HTTP, GORM, Electron, or provider SDK shapes.
- `core/app` owns use-case orchestration, authorization decisions, and transaction boundaries.
- `core/infra/persistence`, provider clients, MCP/LSP, process integration, and HTTP transport are adapters behind focused interfaces.
- Goroutines inherit a parent context and have bounded output/backpressure and deterministic shutdown.

### Agent tools and extensions

- Core owns a validated prompt registry composed from embedded Markdown defaults and private global managed overrides. Each consumer resolves a stable prompt ID through one immutable execution snapshot. Managed files carry content only; code owns category contracts, variables, required/disable/delete policy, structured wrappers, parsers, permissions, and capability enforcement. The associated-subagent explanation is code-generated from the effective validated allowlist rather than resolved from a managed prompt ID. Invalid working files remain inactive and expose only safe diagnostics. Agent-mode persistence references prompt IDs after schema v9, while existing project runtime files remain the final project-scoped overlay.
- Core composes the effective Agent-mode catalog from code-owned built-in defaults, schema-v8 global definitions, and project runtime configuration in that precedence order. Management RPCs may create user modes or replace/reset visible built-ins, but their DTOs and stored payloads exclude toolsets; built-ins reattach code-owned capabilities and custom global modes receive only the safe default before an optional project policy overlay. Primary-capable definitions may own a bounded subagent-ID allowlist. Core validates its effective references, omits delegation when empty, generates narrowed Provider prompt context and tool schema when non-empty, and revalidates each target before forking through the existing bounded child-session executor. Hidden internal workers remain protected and session/association references are checked before custom deletion or role changes. The renderer presents eligible associations through a multi-select dropdown and submits typed definitions, but never owns prompt, capability, permission, or delegation truth.
- The default coding Agent contract consists of seven execution/coordination tools, `read`, `exec_command`, `write_stdin`, `edit`, `write`, `update_plan`, and `ask_user`. Workspace construction registers those seven in stable order, includes them in every eligible primary request and immutable Tool Snapshot, omits them from global management, conversation activation, and composer resource selection, and rejects or ignores attempts to disable or replace them, including legacy persisted preferences. The primary Agent does not receive complete Skill, MCP, extension, or optional-tool catalogs by default; it receives `resource_resolve` and asks the Host to inspect or activate optional resources only when the visible surface is insufficient. Core exposes selected MCP, extension, and optional tools as ordinary Provider tool schemas in the immutable Tool Snapshot, and exposes only the filtered Skill catalog plus its `skills_list`/`skills_read` access tools for the session. Reading a selected Skill's `SKILL.md` remains a normal primary-Agent action against the filtered catalog rather than Host preloading the full Skill body. Extension-context resources selected by the same Host path materialize through the conversation-active instruction path. Other Host Agent-control, goal, and automation executors may enter only through a versioned dynamic contribution with ordinary trust and snapshot checks. Code-owned Provider-declaration and Provider-account tools may be registered dormant outside that default surface; they cannot enter auxiliary/manual selection and become request-visible only through an eligible effective route and immutable Tool Snapshot.
- Codex integration has three capability layers: model-catalog declarations, a built-in ChatGPT Codex OAuth account adapter, and Host-bundled system Skills. The account adapter alone may activate `image_gen.imagegen` and authenticated Codex usage; every fallback route rebuilds the effective tool set. System Skills use the ordinary Host progressive-disclosure path and carry no execution authority.
- Core also registers `grep`, `find`, and `ls` as non-default standalone built-ins. Global management may hide them, a conversation may enable them manually, and `resource_resolve` use mode may select them for the conversation automatic set; the active Execution Environment owns their implementation and Aivo never falls back to local files after another environment is selected. The removed development identities are display-only historical facts, not execution aliases.
- Provider model catalogs with a dedicated structured-capability parser persist exact known capability dimensions separately from their boolean values. Anthropic may additionally persist an explicit known native-server-tool set; Mistral, OpenRouter, and Cerebras declarations establish only client-defined tool-call eligibility. The authenticated ChatGPT Codex catalog may establish allowlisted compatibility facts for the built-in OpenAI OAuth route: context/compaction limits, reasoning and verbosity choices, input modalities, service tiers, parallel-tool and original-image-detail support, Responses Lite selection, web-search representation, and `shell_type` gating of the existing canonical `exec_command` function. Core performs one best-effort first-use sync when authoritative declaration metadata is missing or older than its Host-owned freshness window. An explicit returned value overrides legacy static metadata for its dimension, while omissions remain unknown. Only an allowlisted Provider/transport/authentication adapter may turn a declaration into a tool; generic `tools`, `function_calling`, and `supported_parameters` fields cannot do so. Ordinary Codex Responses search is injected directly as a Provider-hosted tool outside the Registry and Tool Snapshot; Responses Lite and explicit local routing use the dormant canonical permission-controlled `web_search` executor backed by the authenticated Codex search operation. Other Codex-declared local tools remain local Registry executors and must enter the active immutable snapshot and ordinary permission path. Shared OpenAI API-key routes ignore cached Codex declarations, and remote prompts, experimental names, and Agent-policy fields remain inert.
- Every executable tool has one canonical ASCII name matching `^[A-Za-z0-9_-]+$` with a 64-byte maximum. Registry and Manifest validation reject invalid names before catalog or snapshot assembly; Provider adapters use the canonical name unchanged and own no wire alias codec.
- Core's global tool-preference store owns a bounded future-selection visibility set of canonical concrete tool names other than the required core tools. Management catalogs annotate hidden registrations, while conversation choosers and auxiliary candidates exclude them. Explicit groups are projected from the remaining eligible members; a group-level UI switch applies the requested state to every current member. Existing conversation selections remain stable; source lifecycle and the current immutable Tool Snapshot, rather than the global visibility switch, own execution eligibility. A preference-read failure blocks new automatic/manual selection instead of silently exposing candidates.
- Each conversation stores independent manual and concrete filtered automatic tool-name sets plus one filtered visible Skill set. Composer `@` mentions and tool-picker changes are explicit user activation: Core validates them directly, activates selected tools/MCP/extensions as manual tool names, expands selected Skill groups to their current available members, activates selected Skills as session instructions and visible Skill-catalog entries, and initializes the automatic set without consulting the auxiliary model. The first primary request for an uninitialized conversation includes no optional automatic resources. When the primary Agent calls `resource_resolve`, it must choose `inspect` for summary-only inventory or `use` for persistent activation. A registration with no group metadata becomes one individual candidate even when it shares a source or namespace with other tools; a grouped candidate expands all current eligible members. Inspect returns only typed extension/MCP/tool/Skill/context resource summaries and does not inject executable schemas, create request-only snapshot members, or persist automatic names. Use persists every member Host expands from selected tool groups and each selected individual tool. Selected MCP, extension, and optional tool resources replace the filtered automatic tool set and are injected only through ordinary Provider tool schemas. Selected Skill resources replace the filtered visible Skill set, and selected Skill groups expand to all current available member Skills before that catalog is rendered; full Skill bodies remain reachable only through Skill access tools or explicit active Skill loading. Selected extension-context resources are added to the conversation-active instruction state and injected into the primary request. Core validates and expands resources before atomically persisting use selection. The visible resource result contains only typed extension/MCP/tool/skill resource summaries and lifetime; each selected tool group appears once with a member count, each selected Skill group appears once with a Host-owned group ID/name, and each individual or instruction resource appears once, while concrete grouped members stay internal to session state and Tool Snapshots. Replacement is non-cumulative and does not alter manual state. Before every primary Provider request, the Host refreshes readiness for enabled sources and freezes only eligible core, control, manual, automatic, separately authorized mode registrations, filtered Skill catalog resources, and conversation-active instruction resources in the Tool Snapshot and model context. Later catalog changes do not mutate an existing automatic set.
- Long-tail tools, policies, environments, context resources, and Web views enter through versioned language-neutral extension manifests and protocols. Discovery and trust do not execute extension code.
- Required Host-owned Agent capabilities may ship as trusted built-in Manifest v2 extensions. Their contributed executors are `tool` resources rather than user-installed extension sources and may be individual or explicitly grouped through `contributes.toolGroups`; `aivo.projects` is one explicit group, while `aivo.tools` remains individual. Neither expands the four unqualified primitive registry.
- The trusted `aivo.tools` built-in contributes only a non-mutating, turn-owned MCP registration proposal executor. MCP source inventory and concrete-tool metadata remain Host management and auxiliary-selection inputs rather than a primary-Agent listing executor. Only the privileged Host can confirm an exact proposal, persist a source disabled, probe it, and make it globally enabled and ready; the built-in cannot grant its own authorization, handle raw secrets, or populate cross-session manual activation.
- The Host auxiliary resource resolver receives only user intent and bounded single-line `kind:id：display-name｜description` entries, one per explicit tool group, individual tool, Skill group, individual Skill, or extension-context resource. Tool-group lines never include member tool names, and Skill-group lines never include member instruction bodies. It accepts only a strict JSON object whose `resources` contain unique exact typed resource IDs; reasons, extra fields, and concrete members of a group are invalid. Inspect mode uses Host-side catalog matching to return bounded resource summaries without exposing schemas or activating tools; use mode validates and fully expands returned tool groups while mapping returned individual tools to themselves, and expands returned Skill groups into the filtered visible Skill catalog. A blank MCP group description uses the bounded deterministic assembly of every current eligible member name and description; a blank extension group description remains blank. Registration identity, group membership, eligibility, lifetime, and expansion are Host-owned, and descriptions are untrusted data. MCP, extension, and optional tool selection filters the primary Agent's direct Provider tool schemas to the selected set. Skill selection filters the primary Agent's Codex-style Skill catalog and Skill access tools to the selected set; extension-context selection materializes conversation-active instruction resources.
- MCP description generation is a separate explicit Host management operation. Core reads the complete current stored discovered-tool catalog, projects only bounded tool names and descriptions as untrusted data to the configured auxiliary model without executable tools, and returns a normalized unsaved draft. Connection configuration and credentials never cross this model boundary; empty or over-bound catalogs fail instead of producing a partial or inferred description.
- Composer resource mentions cross the desktop submit contract only as bounded typed kind/ID references. Core validates the complete set before user-event creation, applies project references through immutable session association, directly merges Skill and tool references into that session, expands extension/MCP references only to the source's currently registered globally eligible tools, and marks capability activation as explicitly user-selected rather than auxiliary-selected. Visible prompt text and renderer display metadata are never authorization sources.
- The composer's combined local file-or-directory action is separate from resource-reference submission. Electron main owns the native chooser and reads file bytes only from the exact path returned by that chooser; preload exposes only a bounded file payload or selected directory path. The renderer routes files through existing attachment capability validation and directories through existing project registration/context selection.
- Extension processes, services, streams, calls, views, and artifacts have explicit owners, bounded queues, cancellation, draining, and deterministic teardown.
- A supervised local service may use a fixed validated loopback URL or bind port zero and announce its owned endpoint through one bounded versioned readiness record. Core owns the current-generation endpoint and bearer, rejects non-loopback or malformed announcements, and View resolution never trusts renderer or tool-result endpoint data.
- A Manifest v2 `views[].tools` association is resolved by the Host into optional bounded tool-detail metadata; renderer or extension result payloads cannot author backend origins, credentials, routes, or privileged surfaces. Electron may attach an isolated `WebContentsView` over a renderer-owned inspector content rectangle, but the Host-owned header, bounds, lifecycle, and fallback remain native.
- An attached embedded View is reused only while its owner plus Host-resolved extension/View/surface identity is stable. Electron main owns a monotonic mount revision and bounded selected-call context; context-only changes notify that one isolated WebContents without navigation, while identity changes and close paths retain full teardown.
- The extension loader accepts only the exact Manifest/API `2/2` pair and rejects v1 or mixed versions without a compatibility adapter. A v2 service may declare `runtime.messaging`; Electron main then brokers only that extension View's bounded `aivoExtension.runtime` one-shot messages and named long-lived Ports to fixed well-known endpoints on the current Host-resolved service generation. The Host owns bearer injection, connection IDs, limits, cancellation, and teardown; the page never receives the backend endpoint or a generic Aivo RPC surface.
- Local extension installation is a Host-owned preview/copy/confirm operation. Electron selects a source directory; Core validates and hashes without execution, revalidates the exact confirmation, copies into a private integrity-addressed staging directory beneath the platform application-data `Aivo/Default/Extensions` root, reloads the copy, and atomically publishes only the matching generation. Explicit isolated database stores may use a database-sibling root. Core alone grants trust, persists and restores the managed installation, migrates exact former-root packages through the same verified copy path, retains old generations until safe cleanup, and scopes uninstall or migration deletion to an exact Host-owned extension directory. Renderer, model, and extension content cannot choose destinations, write managed packages, delete files, or mint trust.
- Isolated extension Web content reaches privileged behavior only through a versioned Host bridge and validated manifest-declared actions.

## Contracts and errors

- New public resources use versioned `/api/v2` contracts. Existing RPC methods may remain as tested compatibility adapters during migration.
- Stable errors distinguish validation, unauthorized/forbidden, not found, conflict, dependency unavailable, cancelled, and internal failure.
- Error responses include a machine code, safe user message, optional field details, and operation ID.
- Exhaustive request/response shapes are owned by code; specs own behavior and compatibility rules.

## Observability

Important operations record structured lifecycle events with operation ID, duration, cancellation reason, and safe dependency classification. API keys, refresh tokens, authorization headers, raw secrets, and sensitive raw prompt/tool payloads never enter logs or diagnostic exports.

## Compatibility

During a v2 slice, a compatibility adapter may connect new UI contracts to stable application services. Every adapter needs an owner, removal condition, and regression test. A v1 contract field or persistence object is not removed until migration and rollback evidence for its replacement passes.
